# 决定这本模组怎么切

你拿到的不是整本书，是一份**测量**和**几页原文** —— 那几页最可能写着这本书自己的
结构。你的任务是据此给出分节方案。

## 只回一个 JSON 对象

```json
{"sections": [
  {"section_id": "england-london", "title": "England (London), 1925",
   "pdf_index_start": 179, "pdf_index_end": 296,
   "reason": "第 11 页的 BOOK STRUCTURE 把它列为七个核心章之一"}
]}
```

没有 markdown 围栏，没有前后说明。

## 硬约束（机器会逐条查，不过就打回）

1. **每一页恰好属于一节** —— 不重不漏。漏掉的页，其中的场景、NPC、线索会从图里
   整个消失，而下游分不清「书里没有」和「没人读过」。
2. **没有一节超过 `section_budget_chars`** —— 超了那一节就没法交给模型读。
3. `section_id` 是 kebab-case，1–64 字符，互不重复。

## 怎么决定切在哪

**先看那几页原文。** 一本书通常自己说了它是怎么组织的 —— 目录、章节导读、
「本书分为七章」这样的句子。书自己的分法优先于任何机械切法。

**再看测量。** `heading_depth_cuts` 告诉你按每个标题层级切会得到多少节、最大一节多
大。它是参考，不是答案:有的书标题层级干净，有的书文本层把一千多行都标成了一级标题，
那一列数字会明显不合理，你应该看得出来。

**目标是「最少的节数且都装得下」**，不是切得越细越好。一节对应书里一个自成一体的
部分——一章、一个地点群、一条事件线——比切成一百个碎片更有用，因为图里的边往往
落在同一节内部。

**某一节实在太大就再切它一层**，但仍然按书自己的结构切（章下面的小节），不要按页数
硬切——那会把场景和定义它的文字割开。

## 不知道就说不知道

如果那几页没有透露结构，`heading_depth_cuts` 也看不出可用的层级，不要编一个。
返回你能确定的部分，并在 `reason` 里写清楚哪一段你没有依据。宁可让人补一页原文，
也不要给一个看起来合理、实际把书切碎的方案。
