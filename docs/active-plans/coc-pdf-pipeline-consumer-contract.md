# coc-pdf-pipeline 消费端契约修复（2026-08-13）

> 管线在仓库之外（`~/.pi/coc-tools/coc-pdf-pipeline`，AGENTS PDF 契约禁止仓库内
> PDF parser），消费端是 `plugins/coc-keeper`。本文记录一次针对**两者之间契约**
> 的修复：32 本模组全库重抽，管线侧 9 次提交，仓库侧 3 次提交。
>
> 一句话：**一个与消费端毫无关系的判据，恰好在决定内容能不能到达消费端。两边各自
> 都对，中间断了，所有校验器全绿。**同一形状出现四次。第五次修的时候方向错了，
> 被用户纠正——不是把判据问得更准，而是**把判据整个删掉**。

## 2. 四个同形缺口

编号有意义：不是四个独立 bug，是同一形状的四次显现。

### 01 字段名不在投影白名单里

判据「字段叫 `keeper_notes`」，卡住「场景的全部可玩机制」，规模 68 个场景。

引擎给守秘人的投影是写死的八字段（`coc_toolbox.py` 的 `scene.context` 生产端）。
上一轮修过一次，但只修了 `pressure_moves`——校验器注释里把八个字段一字不差列着，
只检查了一个。**写下合约不等于执行合约。**

### 02 门写成了散文

判据「`scene_edges[].when` 是字符串」，卡住「整张场景图的解锁」，规模 538 条边全失效。

引擎把不认识的条件一律转成 `narrative`，而 `narrative` 永远判假。跑出来的：

```
toomany       20 条边 → 全部 narrative → 线索全发现 + 时钟拉满 → 解锁 0 / 13
the-haunting  56 条边 → clue_discovered 11 / always 43 → 当场解锁 6
```

**这一条最后的解法不是修，是拆——见第 4 节。**

### 03 wave 顺序与引用关系不一致

判据「提示词说『已经抽好了』，而文件正在并行写」，卡住「对话路由与 NPC 事实」，
规模 62% 的线索→NPC 引用悬空（84 条里 52 条，19/32 本）。

clue-graph 被要求「从 npc-agendas.json 复制 npc_id」，两者却在同一 wave 并行跑，
抽取器只能照页面上的名字自造 id：`npc-aedel` 实际叫 `npc-adele-mac-gell`。

wave 改为跟随引用关系：无引用（npcs/meta）→ clue-graph → story-graph → dynamics。

### 04 卡司按「印没印数字」筛选

判据「模组有没有给这个角色印属性」，卡住「整个会说话的卡司」，规模全库 76 人。

同一份提示词两条规则打架：「一个属性都没有仍是合法的 `npcs` 记录」对
「`incomplete` 装的是模组完全没给数字的角色」——后者是任何模组里大多数人的状态。
`adventus` 的 `npcs` 因此是怪物图鉴（疯狂市民、暴徒、拜亚基、无骨者化身），13 个
有台词的角色在 `incomplete`：向导奴隶图拉、铁匠之子赛维厄斯、地方长官奥克塔维厄斯。
**而仓库里没有任何代码读 `incomplete`。**

判据换成「在戏里有没有戏份」后：全库 `npcs` 170→480，`incomplete` 76→63。

## 3. 每修一次就长出一条新的省事路径

| 加的检查 | 被怎么绕过 | 代价 |
|---|---|---|
| `when` 必须结构化 | 19/20 写成裸 `always` | 丢掉模组原话，且一次全开 |
| `npc_question` 必须有 `npc_id` | 改标成 `event` | 三段对话离开游戏 |
| 改问「玩家知不知道这地方」+ `revealed_by` | 两条门都指向**去了才拿得到**的线索 | 又锁死 2 个场景 |

**修法不是去文本里匹配关键词**（那是硬编码语义分类，换个说法立刻失效），
**是把标签能买到的好处拿掉**。但这条路走了三轮之后仍在长新的逃逸口——

## 4. 转折：不是问得更准，是把判据删掉

用户的判断：*「门写成散文是模型的特性，这不是约束模型，而是重新设计这个所谓的门。」*
以及后来更进一步：*「不能设成硬门，应该用语义的方法建立连接。」*

支持这个判断的两个数字：

- 485 条边里 **350 条编译成 `always`**——翻译本身是空转；
- 79 条 `narrative` **永久锁死 42 个场景**（18/29 本，线索全发现、时钟拉满也打不开）。

而且门从来拦不住 KP：每个读 `unlocked_scene_ids` 的地方，要么往里加，要么用它决定
**给玩家提供哪些去处**；`scene.move` 是警告后照走。**锁的净效果只有一个——把模组
本来要玩家去的场景关死。**

所以边上现在只剩一个字段：

```json
{"to": "...", "kind": "travel", "transition": "<模组原话>"}
```

编译成 `{"kind": "always", "description": <原话>}`。全库 **607 条边全部 always，
缺原话的 0 条，旧字段残留 0 条**。永久锁死那一类**由构造消失**。

**没有分类字段了，所以没有东西可以规避。**前四次逃逸都围着某个分类字段发生——字段名
在不在白名单、条件是哪个 kind、线索标成什么 delivery、角色为什么 incomplete。

顺带修了消费端一处：`coc_exit_conditions` 原先只给 `narrative` 保留 `description`，
恰好把原话从所有真正的门上剥掉。现在所有 kind 都保留，KP 在 `scene.map` 上看到的是：

```
negotiations -> lake-drowning-ritual
   贝尔坦节前三夜，若成功通过侦察，玩家会注意到一大群人举着火把离开了布多纳兰姆。
```

## 5. 拆了门，衔接由什么承担

用户追问：*「门拆了，但是这个不能空着啊，衔接的要有替代的方案。」*以及
*「可以参考电子游戏，他们都有主线故事，只有达成某个条件才能推动后续剧情。」*

研究结论：**引擎里本来就有两样东西，都没接线。**

**其一·线索账本（场景级）。** `coc_director_apply` 在 `exit_conditions` 为空时回退到
「这个场景的线索都拿到了吗」，发 `scene_exit_ready`。而我给每个场景填上散文，走了
第一个分支、条件恒假，**把唯一的自动信号关掉了**。修法：`has_machine_condition()`
区分「声明了机器条件」和「用文字描述了结局」，后者保留回退。

**其二·主线目标（故事级）。** `clue-graph.json` 的每个 conclusion 就是一个任务目标：
线索是证据，`minimum_routes` 是完成阈值，`coc_belief_state` 早就在算达成判定。全库
**130 个 core 目标，平均每本 4.3 个**。但 `answered_question_ids` 只在认知子系统内部
流转，进不了 CUT 评分，也进不了 KP 的投影。

接上之后，衔接是三层：

```
判断谁做          用什么                                    覆盖
──────────────────────────────────────────────────────────────────
账本（机器）      场景线索给完 → exit_ready，CUT 0.8        257/386 场景（67%）
主线（机器）      core 目标全达成且非终局 → CUT 0.7         130 个目标，30/31 本
KP（语义）        戏剧问题回答了没有 —— 手里有原话与目标进度  全部
冷场（兜底）      stalled_turns >= 2                        全部
```

**加压不设卡**：0.7 低于账本的 0.8，`state.move_scene` 依然从不拦人。游戏里主线条件
卡的是章节推进，不是每扇门——之前的错误就是把锁挂在了门上。

## 6. 验证方式

四次逃逸全是「0 findings 通过」的，所以绿灯只是必要条件。

- **在消费端验。** 把 IR 真装进战役、调 `scene.context` / `scene.map`、用仓库自己的
  `evaluate_unlocks` 跑解锁模拟、把推导的 affordance 喂给真正的 action resolver、
  在真实战役上跑 `apply_plan` 看 `exit_ready_scene_ids`。`roll_gate` 就是这么发现
  不能发的——消费端对形状不全的 roll_gate 直接抛异常。
- **跑完整的一本，不是改动的那一个文件。** 循环门那个洞是「只重跑 story-graph」时
  看不见的，跑完整一本立刻炸出来。
- **配对样本回答「是不是缩水」。** 抽样 5 本时场景数全部下降 8–29%，看着像合约变重
  的代价；全库 30 对配对是下降 9 / 上升 10 / 持平 11，中位 +0%。5 本样本会给出错的
  结论。
- **人工回原文核。** 抽新写的 `transition` 逐条比对，例如 `pale-god` 的「读过笔记
  以后，探索者很可能会出发前往 Martensen 大屋……笔记后一半聚焦于相当接近阿克罕的
  大屋并写下其地址」——与第 4 页原文逐字对上。

## 7. 两次「量出来的假洞」

同样重要，因为它们的数据都很漂亮。

**其一（上一轮）**：全库 139 页有属性块特征却不属于任何 `entity_stats` 分区，涉及
29 本，看起来是系统性 OCR 缺口。抽查三页发现**属性数值本来就读得到**，只是页面短。
那个检测器会把 22 个健康页面送去重跑 OCR。没有发布。

**其二（本轮）**：19 个场景「NPC 在场、而该 NPC 名下挂着线索却没列进
`available_clues`」，回填后覆盖率 67%→75%，新增 274 条关联。回原文核三例，
**三例全是抽取器对、我错**：

```
adventus scene-villa-morning   clue-gaius-lying「识破他在为船难说谎」
                               → 实际挂在 scene-boat-feast。船难还没发生。
children ending-aborted-goddess clue-psychology-evans → 挂在 holingworth-mill，调查阶段的线索
bad-moon whitehaven-meeting     clue-niles-slideshow → 挂在 classified-briefing，下一个场景
```

回填会把船难之后的谎言放进船难之前的早晨。**没有发布。**

> 数据能告诉你有多少，不能告诉你对不对。两次假洞都是「量完就差发布」，都是抽查内容
> 才推翻的。

  不属于任何场景。
