## 产品想达到的体验

这是由 AI KP 主持的高自由度文字 TRPG，不是只能在预登记关卡间跳转的电子游戏。玩家说自然语言：离开房东办公室、找个便宜旅馆、进入前厅、在柜台旁站住、走到窗边看外面、等十五分钟再回来，或者进餐馆吃饭、向店主买东西。模组写过的地点与模组没写过的普通地点都应该能合理探索。

模组可能只提供名称、用途或线索，未写可见外观。KP 应结合时代、城市、建筑用途和既有事实补全。例如1920年波士顿的小餐馆，玩家需要在脑内构建门脸、入口、空间形状、柜台与厨房的相对位置、桌椅材质、照明与生活气息。可搜历史资料，但资料只覆盖一部分时，也应有合乎背景的想象补全，不把资料缺口直接展示成空白，不让每个地点都变成现代铬饰霓虹美式 diner。模组地点同样需要补全玩家视角下缺失的可见场景。

同一旅馆应可逐步具备前厅、客房、餐厅、楼梯、窗户等结构。重访时保留同一身份、布局和玩家造成的变化。一个角落不一定要升级成完整房间；“看柜台”与“走到柜台”有区别。原先在门外看见两人争吵，入内从窗边再看，应有机会看见同一个事件，或者合理知道已经发生变化。不同视点的旧观察、当前状态、未见事实需要区分。离开后再遇 NPC，或 NPC 因玩家影响追来，应该有连贯因果；目前并未完整验证这些能力。

用户要求地点增强做成可迭代、可迁移的 Enhanced Locations Mod，并允许配套调整内核。另一个诉求是：不要每轮把地点、造景、移动的全部工具说明混在巨大 apply 里；相关事件发生时再加载细节。

## 当前领域模型与持久化

逻辑上区分：持续地点 Place、地点内空间参照物 Feature/Anchor、人物位置 Position、包含/通路/感知关系、当前剧情场景、观察记录及持续事件。

具体实现仍复用了普通图里的 scene/location 节点：Mod地点投影为 kind:scene，并以 world.active_scene 作为当前地点。Mod数据放在同一战役 world.mods.state[provider.id].locations（schema1），包括 places、features、position、relations、observations、situations。人物位置主要沿用既有 world.npc_presence；地点Mod没有复制一套NPC世界。

- 新地点由内核产生持久ID。展示名/别名用于模型引用。子地点用“父地点 / 子地点”限定名；叶名优先从当前结构局部精确匹配，歧义要求限定名。不是跨世界名称模糊匹配即自动合并。
- 父子关系和可通行、是否有真实障碍、是否已加载来源材料是不同概念。新地点 within 缺省为空，不默认归属刚离开的房间；不需要预生成整栋楼。
- 已有地点不能通过 additions 描述覆盖原有外观，只能补缺失参照物。feature 命令改已登记 feature 的 state/passable。
- position 表达当前地点+at参照物+relation（开放文本关系，避免所有动作都写成 beside）。这个存储是当前队伍位置，NPC仍归现有presence处理。
- 关闭Mod后已保存的地点记录仍可读；增强写能力是否可用取决于活跃能力提供者/版本锁。完整关闭与迁移路径仍需独立验收，不能只凭设计承诺。

## 当前工具入口与执行流程

统一闭合领域命令定义在 shared/place-structures.ts：

```text
place inspect {name?, at?, sense?, need: context|contract|observation}
place move {to, at?, relation?, via?, travel_band?, additions?}
place establish {additions}
place feature {to, at, state?, passable?}
place relate {relations, additions?}
place observe {to, at?, sense:sight|hearing, access:clear|limited|blocked,
               scope, facts[], view?, people?, situations?, additions?}
```

兼容旧 op:inspect / op:submit 包装；主原生模型接口使用 action 分支。新地点、局部参照物可以在 move/observe 的 additions 中提供，避免固定“先造景再移动”的多轮仪式。establish 仅登记环境，不代表玩家造房子或已经走进去。observe 不移动人物、不创建NPC、不结算物品/检定。

同一命令能通过独立place工具、混合apply事务、原生output决策包进入同一内核staging处理器。独立工具不是第二个事务引擎。混合现金/钥匙/入内等不可拆交易可以通过同一原子批次提交；拒绝整个技术批次不会偷偷保留半个移动，之前独立成功的收据仍保留。

当前KP可先提交真实中间步骤，不发布正文。已知效果的最后一次移动+观察可在一个output中一起提交；一个output最多一个最终移动目的地。移动→观察→等待→返回这类需要时序的行动，先place move/observe，再apply time，最后output提交剩余返回/观察与NPC沟通。最后由隔离的作者阶段根据已结算结果生成玩家正文。作者可补兼容可见质感，但不能自行实现移动、扣钱、新人物到场或新互动参照物。

## 空间观察、时间、事件连续性

- 感知关系为有方向的 from{place,at?}→to{place,at?}，区分 sight/hearing。观察的 to/at 表示观察目标；实际观察者的位置来自当前状态，不能把目标当成隐式移动。
- 跨地点观察需要已知或本次补充的合乎空间条件的view/relation。关系不自动赋予物理通行权，也不是全连通的视野地图。
- observe 收据记录 from/to、sense、access、scope、facts、people、situations、observed_clock。被看见的NPC必须已经存在并在目标地点；不会因被观察而传送到玩家身边。
- 世界状态 observations 目前按“目标空间点+sense”保留最近一次结算；完整历史来自不可变逐回合收据。只读观察上下文提供最近4次已交付观察、最后一次成功可见观察、最近已结算但未必交付的观察，以及与当前游戏时间的差值。
- situation按目标空间点+归一化名称复用，记录参与者、ongoing/ended/unknown、上次判断时钟。elapsed>0可提示重新判断；没有每隔N分钟强制事件结束或自动跑一个全世界模拟器。
- KP结合已有NPC活动、意图、动作后果和时差决定状态是否变化，真正的NPC移动/互动仍须既有NPC效果。仅观察不替代人物行动。
- 实玩曾将“窗外街道”写为 to=旅馆、at=临街窗、scope=窗外街道；而结构定义把to/at当目标，实际窗口通常应是观察者位置。我们尚未全面验证这种表征在跨视点回看同一事件时是否产生身份/目标分叉，请自行评估。

时间分为：移动拥有的行程时间；玩家明确等到某个时刻的until；玩家明确选的分钟数；按规则类别计算的普通活动成本band。行程时间不能重复扣。until应由内核按当前绝对时钟计算，不由模型估算分钟。时间类别如momentary、quick_observation、brief_activity有规则定义与范围，内核掷出具体值。

## 选择、准入与完成检查

KP理解自然语言并提出行动；Jev用于有限相关性、绑定/准入等语义判断；内核负责规则算术与事务。当前存在多层检查：

1. 每输入一次地点相关性判断，决定是否加载移动/feature/观察细节；只决定上下文，不构成行动授权。
2. 对实际提案，选择与显式限制/先决条件分别做Noul判断；当前选择概率至少.60，限制概率至多.40才允许，未确认时不执行。
3. 提交后分别检查玩家选中的移动、持久feature变化、观察是否有实际操作/收据或真实障碍。到门口不自动代表进入；走过去不自动代表已仔细看清。
4. 路线检查读取实际当前位置、已结算步骤以及有条件的批内前序位置；后序返回不能证明前面的到达已经发生。

这份材料报告这些门槛是当前事实，不要求你把这种多层设计当成不可改变的前提。正确拒绝未选择的破窗、额外研究、额外等待本身不是Bug；错误提案反复产生、正确选择被误判、恢复/交付缺口与玩家无法完成行动则需要系统性判断。

最新时间提问的演进也可能值得批评：v21统一强调“已选活动的普通耗时不是另选暂停”，解决了一次局部返回计时误判，却使明确until等待无法确认；v22按band/until/minutes的闭合字段分别提问，而不是从自然语言正则分类。回放中正确01:15得到.84，错误02:15得到.57（仍保持不执行），未选等待.13。但这仅是诊断回放，v22尚无原App实玩验证。

## 上下文和生成/提供者接线

- 安静会话保留精简place入口；地点相关输入/实际调用再披露完整typed schema、局部图与Mod段落。缺少登记/来源尚未就绪不应该变成虚构世界中的墙。
- 宿主历史投影只省略可识别的旧地点说明块，原始记录保留，工具调用-结果配对与provider要求的续写协议保留。声明、执行器、引导文本、世界事实、历史回放和缓存消耗是不同层。
- 来源lookup pending时附带只读registered_location身份参考，避免为了粉饰普通外观反复等待背景读书。身份参考不代表来源已查清，也不授权看见隐藏房间。
- 地点Mod agent.md约19KB，包含身份/结构、移动/局部位置、连续性与权威、空间观察等按需段落；“Place description for the author”作为reference段单独提供给最终作者。细节描述引导同时适用于模组和即兴地点。
- 一次实际Grok请求曾测到place详细声明10,126字节、output约74–76KB；某回合整体请求投影约385KB、工具schema约168KB。是JSON字节，不等于实际provider token或延迟归因。地点拆出apply并未让整个回合上下文自然变小。
- MiniMax Messages与Grok Responses有不同wire格式。曾只替换Messages的output.input_schema，Responses仍发静态旧schema，而执行层用动态schema校验；已修同源绑定。还处理根schema必须是object、空enum/Never在request端省略不可用选项、分支完整typed array、本地$ref复用防止schema膨胀。执行校验没有因此接受错误类型。

## 过去反复暴露的问题（不要只评最后两轮）

A. 空间/身份/访问：未列出的普通地点被原生已发目的地词表卡住；父级缺省错误；已知地点翻译后被重复建造；bounded catalogue被局部feature占满；同名房间；把来源未加载当地点不存在；把区域包含误作免费可达。已做共享入口/身份/目录公平投影等修补，仍需检验领域边界是否正确。

B. 工具/协议：inspect/move/submit字段混用；JSON数组被输出成字符串；根union被provider拒绝；native move与place字段串线；新NPC slot未经登记就出现在观察；place/输出声明与执行校验漂移；为了完整分支复制schema，又引起请求容量/最新工具结果保留失败。请求端$ref共享后容量回归通过；兼容性仍应看真实wire而不是源码schema。

C. 事务与行动顺序：早先自动移动前缀抢在feature行动前执行；当前姿势已到达但最终交付失败后又要求重复移动；移动收据丢失via，路线完成检查无法证明实际路径；观察曾统一被编译到所有移动/时间之后。最新保序修复又导致scene人数评估早于新人物登记/移动，现已修依赖，仅组件验证。多入口、多次提交与恢复容易让“已完成/未完成”混淆。

D. 准入/成本：局部姿势、普通吃饭、重复观察、NPC活动重写、momentary计时会出现不确定；其中部分确实是额外未选动作，不应放行。单靠增加Mod指导没消除坏提案。采用过“已选目标与已完成收据分开”“位置仅对wait先决条件判断”“把实际活动成本和新增等待分开”等修补，但新的提问可能回归旧场景。

E. 观察/连续性：已有窗户和感知关系被重复定义；把登记环境误作玩家造景；观察把远端人物列成本地人物；旧观察被当现在事实；NPC同一身份未知姓名时重复识别；仅时间过去就重写NPC活动；有移动却漏交付玩家选的阅读/观察。当前分别补了视点、身份、观察完成检查、已交付/未交付观察与时差，但完整跨视点事件连续性尚非稳定验收结论。

F. 描述/来源：餐馆只给名词清单，玩家无法想象布局；来源没写就不补；可见地板描述成“石板（或木板）”；菜单存在但正文遗漏；历史搜索年份把1920错当2026；同一引用年代/地区不适用；hosted search未完整保存server continuation，2013协议错误和空server-only轮询。已有具体修复与成功搜索证据；不是每次进入都必须搜索，也没有证明每个场景历史细节都正确。

G. 跨领域后果：菜单45美分被作者误读成单价又加钱；decimal克隆使数值投影变形；服务已结算但正文说没上菜；回访重演旧开场、持有物回滚；购买/移动/观察状态相互脱节。部分共享投影修复后曾真实完成进餐、付款/武器交接、返回既有地点。这些属于地点与金钱、物品、人物、作者交界，不是地点工具单独能包揽。

H. 可观察性/验收：早期有副本/RPC试验被错误表述成原App试玩，后来纠正；本次当前验收坚持原内置《鬼屋》会话。也出现将中间一次工具错误过早报告为整轮结束的错误，第63轮最后其实完成但超时。不能用报告、假KP、脚本批量回合或单元测试代替真实游戏。原始失败保留，UI正文给可读原因，技术JSON折叠；供应商529/流空闲60秒也需与产品错误分清。
