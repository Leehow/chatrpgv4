三、空间模型：采用可逐步细化的拓扑，不需要完整三维世界
1. 地点、锚点、边界应各自表达一种稳定含义

我认可当前区分 Place 与 Feature/Anchor 的方向，但建议把判断标准说得更清楚：

地点：可以独立进入、停留、管理人物存在或适用局部规则的空间。
锚点：地点内部供指向、站位、观察或互动使用的参照。
边界或通道：连接空间或区域，决定通过、看见、听见的条件。

旅馆和前厅可以是地点；柜台、临街窗通常是锚点；前门连接门外与前厅，是边界。一个角落只有在独立遮挡、停留或互动确实需要时，才细化为区域。

不必提前生成整栋楼，也不必把所有家具登记为实体。玩家的探索可以逐步提高局部精度。

需要避免的是让“精度提升”变成“身份重建”。 例如，玩家开始在柜台后活动，可以增加柜台后方区域；原柜台仍保持同一个对象，不应因系统改了空间尺度而消失或换名。

目前已有 UUID，但 within、feature 所属地点、位置、感知端点等仍大量通过名称 handle 关联。限定名很好用，却不适合承担长期内部身份的全部责任。

我的建议是：

内部关系绑定稳定 ID。
模型使用简短、当轮可读的引用，例如地点引用和锚点引用。

这能同时保留自然语言引用的便利，并减少改名、翻译、迁移和跨 Mod 引用的脆弱性。

普通站位可以保持粗略。窗内与窗外、桌旁与桌下这类有实际区别的位置，则不能被同一个空间点覆盖。

人物位置也应逐步统一查询语义。可以先把现有队伍 position 和 NPC presence 接入同一查询接口，暂不同时重写所有存储。不要为地点 Mod 再建立一套 NPC 位置真相。

四、地点补全：让描写成为可继续游玩的承诺
1. 区分“材料没写”和“材料还没读”

模组只给名称和用途时，兼容补全非常合理；但来源尚未读取时，不能自动推断关键布局不存在。

建议模组导入或首次接触时建立一个轻量索引，至少覆盖：

地点身份及别名；
已知父子结构和重要出入口；
对探索有影响的空间约束；
需要保密的空间信息；
哪些方面确实没有描写。

普通外观不需要每次检索历史资料。时代与地域参考可以成为可复用的背景材料；具体行动依赖的布局、通路和模组秘密，则在必要时读取。

这样才能同时实现：

资料只写“小餐馆”，仍能提供具体而可信的门脸与内部空间；
模组明确写“无后门”，不会为方便玩家离开而临时补出后门；
来源服务暂时 pending，不会被叙述成建筑不存在或前方不可通行。
2. 把空间补全分成三个层次
层次	示例	建议的处理方式
影响行动可能性的结构	出入口、楼梯、主要遮挡、锁、可通行路径	在实际使用前由世界层确立
需要重访保持的外观	柜台位置、椅子材质、墙面、照明来源	建立稳定外观记录，关联来源和视点
当次表达	句式、描写顺序、比喻和节奏	交给作者

这里最容易遗漏的是第二层。

作者描写了“靠窗有一把绿色扶手椅”，玩家下一轮说“坐到那把椅子上”，这应当是正常玩法。不能要求第一轮把所有家具都变成 feature，也不能因它尚未结构化而拒绝玩家引用。

我的建议是：保存实际交付的环境描写及其地点、视点、时间；玩家随后指向其中的对象时，再把对应对象提升为稳定锚点或可交互实体。

这种提升必须保留原先实际表达的范围：

“像银制”不等于确认材质是银；
“看起来封死”不等于确定无法打开；
NPC 说房间里有保险柜，不等于玩家已经看见保险柜。

原文提供可追溯依据，语义绑定仍需要判断。后台摘要可以辅助检索，不能替代原文成为唯一真相。

我建议让 KP 提供少量结构锚点和确定的可见事实，作者负责组织和丰富表达。作者新增的非机械外观通过交付记录保留，后续按需结构化。

需要坦率承认一个取舍：允许作者自由补充具体细节，就无法仅靠执行前的 schema 保证所有新增语义都已验证。 可以限制机械事实、保存原文、约束后续提升，但不应声称这会完全消除描述矛盾。

4. 稳定描述不应妨碍真实改变

禁止 additions 覆盖旧 description，有助于防止重访时重新生成房间。这个保护值得保留。但它还需要配套区分：

首次发现此前未描述的方面；
观察变细后确认属性；
门、家具和建筑实际发生变化；
角色此前判断错误；
管理层修正导入错误。

源模组保持只读，战役中有效的空间状态可以改变。旅馆被烧毁后，旧描述仍可作为历史基底，却不能继续主导当前外观。

五、事件与时钟：让世界按因果变化，让观察只提供证据
1. 持续事件必须拥有独立身份

当前 situation 的复用键是“目标空间点＋名称”，并由 observe 更新 summary、status、participants 和 assessed_clock。unknown 也进入同一状态字段。
source-excerpts

这会给长期连续性带来两个根本问题：

事件换位置，身份可能跟着变。
争吵从街角移到巷口，仍然是同一场争吵。观察目标从“街道”细化为“街角”，也不该自动生成另一个事件。

观察者失去证据，容易被写成世界失去状态。
“从这扇窗看不到那两个人”不等于争吵结束，也不等于世界事件本身进入 unknown。

建议持续事件至少拥有：

独立 ID；
参与者和当前活动范围；
当前阶段；
已处理到的游戏时刻；
下一已知期限或触发条件；
最近变化的原因及相应效果引用。

观察记录引用事件 ID 与对应状态版本，另行保存看到了什么、听到了什么、哪些不能确认。

世界也可以有尚未求值的部分；这应是运行状态，而不是角色认知状态。无需为此构建一个始终完全确定、全城实时运行的世界。

2. 采用稀疏的事件推进

我建议按以下方式推进时间：

行动产生自己的时间成本，或玩家明确选择等待。
宿主找到相关的下一个事件边界。
确定性的到期效果直接执行。
需要语义判断的相关变化交给 KP。
记录本次已处理的时间区间。
没有新决策需要时，继续原行动。

远处无关的事务可以延迟处理；当它们进入当前行动的因果范围时，再补算尚未处理的区间。补算必须有时间和版本记录，避免观察一次就重算一次。

这意味着：

十五分钟过去，可以触发重新评估，但不能直接证明争吵结束。
同一时刻重复观察，不应重新抽取世界状态。
改变视点可以获得新证据。
开灯、关窗、引起对方注意等真实变化，可以改变后续观察结果。

延迟确定普通背景可以与第一次观察在同一次处理完成，但“补全此前未定内容”和“让已有事件演进”应当是不同的语义。

3. 等待必须允许在有意义的时刻中断

“等到一点十五分”通常允许无事时继续等待，却不意味着玩家愿意在遭遇攻击、目标离开、关键人物到达后仍无条件站到终点。

因此，时间推进应到下一个有意义的边界：

出现直接危险；
原行动目标失效；
达成玩家指定的等待条件；
发生需要玩家重新选择的重大变化。

普通钟声、路人走过不必打断。中断策略要围绕玩家行动的意义，而不是每个环境事件。

不能先把十五分钟全部结算，再在正文里倒插一个本来需要玩家于第五分钟作决定的事件。

4. 普通耗时应归属于活动

我建议保留 travel、until、minutes、band 的语义区分，但改变普通成本的产生方式：

行动	时间由谁拥有
跨地点旅行	该次旅行
仔细检查	该检查活动及其规则
吃饭、维修等服务	对应服务活动
明确等待十五分钟	独立等待活动
明确等到某个时刻	独立等待活动，由内核计算差值
局部挪动	按当前规则计时，不额外虚构“暂停”

时间成本绑定活动或步骤 ID，重试同一步不得再次计时。若规则需要选择时间类别，类别可以作为活动参数，但不必重新包装成另一个独立的玩家意图。

这一改动比继续微调 time 的准入问句更有长期价值。

六、执行协议：让宿主跑完“已知的下一段”
1. 将一条玩家意图绑定成有序活动

这里的“活动”是一份轻量执行记录，不是一套新的工作流语言。它保存：

对应的玩家输入；
已绑定的目标与明确限制；
有序步骤；
已提交收据；
当前停点；
待交付结果。

首版可以直接复用现有领域命令与收据，增加稳定的步骤身份和宿主推进逻辑。不要引入任意 args、自由条件表达式、模型生成循环或补偿脚本。

执行前需要检查原话中的目标、次序、限制和必须获得的内容是否被覆盖。此后，完成情况主要按步骤和收据确定。

这里有一个能力边界：如果最初就漏掉了玩家要求的“读菜单”，执行器只能证明它完成了错误解释后的计划。因此，减少重复语义检查的前提，是把首次意图绑定做完整。

2. 一个提交可以包含多步，但不预写未知结果

现有“一份 output 只有一个最终目的地”的限制应退出世界执行语义。真正需要拆分的是未知结果、新选择和有意义的中断，不是“这是第几个目的地”。

以玩家的行动为例：

“走到窗边看看刚才那两个人，等到一点十五分，再回柜台看看老板还在不在。”

可以绑定为：

步骤	目标	执行时确定的内容
1	到已有窗口的室内侧	新位置及该动作成本
2	观察原事件	从该视点获得的实际证据
3	等到游戏时刻 01:15	差值、期间相关事件、是否中断
4	返回柜台	返回位置及成本
5	检查老板是否在场	当时的存在状态及可感知结果

若这段过程中没有真正的新判断，宿主可以连续执行。若第五分钟有人追来，停在该时刻，交付已经发生的经历，让玩家决定下一步。

观察结果不能在最初计划里随意预写；世界状态足够时可以直接生成，信息不足时再返回 KP。模型调用应由缺失信息决定。

3. 编译器只前置纯定义，不重排真实行动

当前 compiler 会按种类重排一部分命令，而且 walk_on 编译后不仅分配身份，还包含 NPC 放置。因此，“人物出现→等待→观察”存在被转为“等待→人物放置→观察”的结构风险。附件不能证明该例已实玩发生，但重排本身是明确的。
source-excerpts

建议区分：

分配实体身份；
在某时刻建立实体存在；
人物实际到场；
从某个时刻的快照评估人数或观察。

只有无时间意义的身份定义可以安全前置。真实行动保持顺序。预览、准入、执行和完成核对应使用同一份逐步状态投影，减少各自重新推断时序。

4. 原子事务与整段行动不是同一个单位

适合原子处理的例子包括：

一次现金与物品所有权交换；
一次钥匙交接与相应权限改变；
建立最小地点并完成到达。

已经走过的路、已经等待的时间，不应因最后作者失败而回滚。

同样，真实游戏失败与技术错误要分开：

撬锁失败仍可能耗时、发出声音，这是游戏结果。
JSON 类型错误不应产生上述后果。
已付款后发现另一扇门锁着，不一定应撤销付款，取决于实际交易语义。
事务未提交，应明确没有执行这一笔；此前成功步骤仍然有效。
5. 允许交付真实的部分结果

turnPacketResult 对 not_landed 抛错，正常结果则给出全部完成的布尔值。这有助于防止虚报完成，但所示接口没有形成完整的部分完成表达契约。材料中的若干回合已经体现出“世界前进了，正文没有交付”的问题。
source-excerpts

目标结果应能够区分：

完成；
遇到真实障碍；
等待玩家选择；
技术中断；
已执行、待交付。

作者可以叙述真实发生的部分。技术中断则至少应由 UI 给出可信状态，例如当前地点、当前时间和未完成步骤，不能让玩家猜自己是否还在窗边。

恢复同一活动时，宿主继续未完成步骤；新的玩家输入可以取消或修改尚未执行部分。已提交的行动保持不变。

6. 交付确认仍是重要边界

取消 output 的物理动作调度职责，不意味着“表达完全没有状态意义”。

位置、付款和观察结果可以先结算。
NPC 计划说的话，在未表达前仍是待表达内容。
已知、已听见、已作出口头承诺，需要依据实际交付记录。
流式中断不能把整份计划对白都标为已经说出。

建议保存实际呈现的消息及已确认前缀，恢复时延续原消息或重新呈现既有结果，避免重新执行动作。后台记忆可以异步，但下一轮应能够直接读取实际交付的原文。

这部分仍需要完整流式提交协议才能判断当前实现是否充分。

七、NPC、物品和服务：共享位置与因果，避免地点系统包揽所有领域
1. NPC 连续性需要任务和知识依据

材料中 NPC 受邀从旅馆来到后院，证明了受邀到达能够发生；它不证明自主追踪、敌意追逐或分头重遇已经成立。
review-brief

自主追踪至少涉及：

为什么追；
知道玩家去了哪里，还是仅有猜测；
何时出发；
沿什么路线移动；
何时可能追上；
玩家换路或进入建筑后，是否还能继续。

这些属于 NPC 与持续事件领域。地点提供空间和路线，时钟推进任务，观察决定玩家什么时候发现对方。

NPC 不能因为进入了新的观察结果，就自动获得到场、身份识别或对话权限。

2. 背景人群可以先保持为群体

当前 guidance 要求 quiet、active、crowded 具有实际 NPC placement。这并不证明必须实例化每个群众，但确实把普通场景人口与具体人物登记绑得较紧。
source-excerpts

建议允许“背景群体”记录人数级别、活动和公共外观。当玩家指认其中某人、与其互动，或其行动产生持续后果时，再建立具体身份。

这样可以描述一间有生活气息的餐馆，同时避免为了证明“不是空屋”而不断制造需要维护的 NPC。

3. 物品与空间锚点之间需要可追踪的关联

一把椅子最初可能只是环境参照，后来被搬走、砸坏或用来堵门。一个墙上挂件也可能被取下放进背包。

目标应是保留同一个对象的身份，并让它按需具备物品、锚点或障碍等能力。物品持有权仍由物品领域负责，地点查询引用其当前空间状态，避免生成“背包里一件、墙上仍有一件”的两套事实。

不需要立刻把所有 feature 变成复杂实体；先把已经会发生跨领域变化的对象接通。

4. 普通服务应有自己的履行语义

当前地点说明详细指导一顿饭如何依次获得物品、消耗物品、计时和付款。它保护了物理效果的完整性，却也让 KP 为日常服务承担底层操作编排。
source-excerpts

我建议为已有服务建立明确的履行命令，由领域处理器拥有：

已确认的报价及内容；
玩家预算或条件；
供应者；
交付或消费；
时间；
付款时机；
实际完成结果。

堂食是否必须在背包里先增后减，应由物品和服务规则决定，不应成为模型每次手工维护的仪式。可带走商品、剩余物品仍使用现有库存语义。

作者收到的是明确的结算结果，例如“总计 45 美分、包含咖啡、已付款、餐食已消费”，不再自行把菜单数字解释成新的金额。

八、工具、Jev、作者与 Mod 的分工
1. 工具语法应小而完整，世界数据按需提供

目前简化入口在部分位置使用开放字段，再让模型通过 inspect 获取完整契约；执行端保持严格校验。这有节省声明空间的作用，也可能把未披露完整语法的成本转化为错误与续轮。
source-excerpts

建议分开两类信息：

操作语法：常用移动、观察、等待的小而完整签名。
当前数据：地点引用、局部结构、规则时间档、相关事件和已完成步骤。

普通场景不应必须先查 contract 才能移动。特殊空间编辑和新能力可以按需加载。

place 名称可以保留，旧 op/submit 也可以作为历史兼容适配；所有新写入应进入同一活动执行协议。最终 output 不再复制各领域的整套执行 schema。

这也避免把新增活动层做成另一个巨大的 apply：活动层只管理顺序和进度，领域参数仍由同一注册定义提供。

2. Jev 适合处理有限语义问题，不适合证明所有执行事实

我建议保留 Jev 的可选价值：

地点身份候选的相关性；
确实存在歧义的目标绑定；
是否新增了玩家未选择的承诺；
对初次行动解释进行有针对性的覆盖或越权检查。

已绑定步骤是否执行、时间是否重复、资源是否足够、路线是否经过某道已知障碍，则交给确定性逻辑。

这不是立即删除所有检查。应当比较两类错误：

错误执行额外动作；
错误拒绝已选择动作。

附件没有提供足够的分数校准和独立样本，因此 .60/.40 不能被视为已经验证的可靠边界。当前覆盖检查也有并行请求，不能把每个预算简单相加来推断总延迟。
source-excerpts

3. KP 与作者的逻辑边界值得保留，独立模型调用需要实测比较

KP 负责意图、世界判断与规则请求，作者负责依据已结算结果表达，这个逻辑分工有价值。

但“逻辑分离”是否必须通过独立作者模型实现，材料尚不能证明。双阶段带来额外串行调用，也提供更清楚的上下文隔离。我的建议是先保持现有作者边界，避免首轮重构同时改变太多变量；之后将单模型工具结算后直接表达作为受控基线，比较遗漏、泄密、事实一致性、文风与总耗时。

目前没有理由再增加常驻造景 Agent、事件 Agent和作者审稿 Agent。

4. Enhanced Locations 应保留，但需要明确能力所有权

目前 provider 选择使用“依赖 locations.v1 的最后一个 Mod”，读端又聚合多个 Mod 的 schema1 状态。单 Mod 环境下可以工作，但长期扩展需要显式区分：

requires：需要什么；
provides：提供什么；
谁拥有规范写入权；
谁可以扩展或覆盖哪项策略；
版本是否兼容。
source-excerpts

我推荐的边界是：

稳定内核契约	Enhanced Locations 及其他 Mod
身份、位置、空间引用、时钟、事务、收据、观察证据	补全策略、时代风格、尺度策略、感知规则扩展、能力说明和表达指导
统一的活动执行与恢复	注册新的领域操作及其处理器
状态版本与迁移机制	内容版本和策略版本

关闭 Mod 后应能保留基本空间可操作性。验收不能只检查“记录可读取”，还要检查玩家是否能离开已经生成的旅馆。

提示词也需要随职责迁移而缩减。API 修正、收据恢复和交易顺序应主要由程序保证；模型说明保留语义判断、兼容补全和视角约束。当前按文本前缀及字符串替换移除旧职责的方式，也应逐步改成显式角色与能力片段组装。
source-excerpts

九、我建议的优化次序

不建议一次替换所有领域模型。最合理的方式是每次完成一条能够在真实游戏中体现价值的完整路径。

次序	改动范围	放行标准
第一阶段：行动可靠完成	稳定步骤身份；宿主持有顺序和进度；普通成本归属活动；部分交付与恢复；解除最终单目的地限制	多步行动按序执行，错误恢复不重复时间、移动和付款；技术失败时玩家知道当前状态
第二阶段：同一事件跨视点连续	独立事件 ID；事件演进与观察分开；保留完整视点；相关时钟边界与中断	门外、窗内、街角观察同一事件；事件换位置不换身份；等待不会越过必须介入的时刻
第三阶段：普通探索持续可玩	稳定外观记录；作者细节按需提升；背景群体；服务履行；物品与空间关联	玩家能引用先前描写的家具，改变它，再离开重访；日常消费和 NPC 互动保持后果
第四阶段：扩展与长期运行	显式 Mod 能力所有权；稳定 ID 引用迁移；长期检索；provider 声明与缓存优化	升级、禁用、重载不破坏既有地点与经历；地点和历史增长后仍能稳定绑定

实际实施中，新的事件和步骤类型从一开始就应使用稳定引用和版本契约，但第一阶段不必同时完成所有角色独立位置、所有事件生命周期和全存档迁移。

已有收据和源材料应保留。旧 situation 迁移时，不能仅凭相似名称就跨地点自动合并；旧 unknown 也不能被无依据地升级为确定的世界状态。

如果资源只能支持第一项改动，我会先做宿主拥有的有序活动、成本归属和恢复交付。它直接减少当前最伤体验的卡住与沉默，并为事件和空间重构提供稳定运行入口。

十、怎样验证这些改动确实改善了游戏
1. 验证可迁移的性质，不只重跑原句
性质	应覆盖的情境
身份稳定	译名、别名、同名房间、不同视点、事件移动
顺序稳定	到场后观察、观察后等待、等待后返回、人物出现后时间推进
后果稳定	支付、钥匙、物品移动、门状态、服务完成、家具被搬走
认知准确	看不见不等于不存在；听到声音不等于听清内容；未知姓名不重复造人
恢复准确	付款后故障、等待后故障、观察提交后作者失败、流式正文中断
自由探索	模组地点补全、普通新地点、未登记锚点、作者细节被再次指向
中断合理	等待期间危险到达、目标离开、条件满足，普通背景变化不中断
Mod 可迁移	升级、关闭、重载之后，旧地点仍能继续游玩

还应加入一种很有价值的对照：在没有新中断和新选择时，同一段自然行动一次提出，与分几次提出，应产生相容的世界结果。观察次数本身不应无故改变事件轨迹。

2. 分开验证三个层面

确定性验证检查状态、顺序、幂等、资源守恒和恢复。

真实模型验证检查意图理解、目标绑定、额外动作、遗漏、语义歧义和描述连续性。应使用不同措辞、不同地点名、不同布局和必要的反例。

原 App 连续游戏检查长期体验。可以先用多条二三十轮的连续轨迹筛查问题，但这些数量只是起步方案，不能当作统计充分性的保证。重点是离开、重访、改变环境、引用旧细节和故障恢复，而不是只做孤立工具调用。

3. 性能指标应与正确完成率一起看

需要记录完整调用时间线：

主 KP 调用次数；
Jev 批次、是否并行及实际墙钟时间；
工具执行和来源等待；
错误、修正和 provider 重试；
实际 provider token 与缓存用量；
作者首字与正文完成时间；
点击发送到完成的总时间。

附件给出的 385KB 请求体、168KB 工具 schema 是 JSON 字节，不能直接换算成 token，也不能据此断定主要延迟来源。
review-brief

原有 120 秒目标应继续按原定义验收，同时统计总成功率、失败恢复成本和耗时分布。失败得快不能记作性能成功；provider 故障可以单独归因，但仍属于玩家实际遭遇的失败。

4. 还缺哪些证据

在作出更强结论前，我最需要补齐的是：

完整移动、时间、NPC、物品和现金处理器。 目前不能据地点摘录断言它们完全缺少某项保护或调度能力。
真实端到端 trace。 用于定位延迟及错误的主要来源。
作者新增外观进入下一轮绑定的路径。 包括原文、摘要、持久事实和对象提升。
流式正文的实际交付与恢复协议。 特别是中途断流时哪些话语被视为已经发生。
Jev 误执行和误拒绝的标注样本。 用于判断哪些检查值得保留，哪些只增加摩擦。
Mod 关闭、迁移及长期会话的证据。 包括同一战役里地点、事件和历史持续增长后的表现。

这些缺口不妨碍提出上述方向，但意味着目前不能承诺某次重构必然达到具体延迟，也不能声称所有历史故障都已找到唯一根因。

我会把下一版的核心放行标准定为：玩家能够稳定回答“我在哪里、怎么到这里、刚才实际做了什么、世界因此改变了什么、还有什么我不知道”。 地点系统的内部结构，应当持续帮助这五个问题保持清楚；普通探索不应再依赖 KP 每轮重新拼接一套工具协议。

改变正门状态；

这还不能单独证明“进入门厅”已经执行。观察目标是门厅，不代表观察者位于门厅。

这里我不会直接判定漏执行，因为片段可能省略了站位、跨门信息或后续步骤。但应核对最终位置与收据：

玩家是在门外、门槛处，还是门厅内部？
跨过正门这一边界由哪一步完成？
“门厅”作为子空间或局部区域，能否区分门内与门外？

门厅不一定必须成为完整的独立 Place，但必须能够表达“已进入”的空间事实。这比最后正文是否写出“你走进门厅”更重要。

三、第 91 轮地图问题：应按用途分派资料，不能按“地图”这个词分派

我会保留 look map 对玩家安全地图的限制。将 Keeper 楼层图直接纳入接受范围，会把一次读取失败变成信息泄漏风险。

这里需要明确三种能力：

能力	读取什么	结果用途
源资料读取	模组 PDF、Keeper 平面图、隐藏布局说明	KP 的后台准备
空间状态查询	已登记空间、边界、当前位置和变化	判断当前行动与观察
玩家地图呈现	已获得的地图或经过裁剪的公开投影	交付给玩家

“地图”是资料形态，并不能决定它属于哪一种能力。

我会怎样修改

首先改 lookup 返回的资源引用，使其同时带有足够明确的类型和可用操作，例如：

这是 Keeper 来源图；
对应哪一页或哪份图像；
可以通过哪项已有宿主能力读取；
不能直接作为玩家 map_view 输出。

优先复用已有的来源读取能力。 从目前摘要还不能判断是该能力缺失、没有正确暴露，还是模型忽略了它，不能据此另建一套读图系统。

其次，第一次误用就应返回可执行的诊断：

这个引用是 Keeper 源图，不是带 region 数据的玩家地图；应通过对应的来源读取能力获取。

仅提示“not a region map”，再列一组玩家地图候选，容易让模型误以为只是名字不匹配，于是换成人类标题再试一次。

PDF 和图像读取继续由宿主承担，内核不需要因此接管文档解析。读取私密资料也不产生玩家观察、耗时或地图获取的游戏结果。

读取正确之后，还要防止资料知识直接变成角色所见

KP 看到完整楼层图，只说明它掌握了裁定所需的资料。玩家仍只能获得当前位置和条件允许的观察。

所以，私密来源图不应直接进入最终作者的普通场景材料。作者应得到经过本轮感知裁定的内容及必要限制，而不是拿着整张内部图自行决定披露哪些房间。

这与“工具是否成功读图”是两个独立边界。

四、观察接口：六条上限应改，但不能把丰富观察全部交给作者
1. 六条不是合理的观察有效性边界

八条短事实可以比六条长事实更简洁、更容易核对。当前限制允许六段各 600 字符，却拒绝八段很短的内容，说明它控制的是分段方式，未有效控制信息量。

更关键的是：把同样的事实从八条合并成六条，世界内容并没有改变，事务却从失败变为成功。

这种表示方式差异，不应该决定一次合理观察能否结算。

我会改成：

以整个观察材料的总量控制常规预算；
保留合理的单项长度限制；
项数上限仅作为较宽松的异常保护；
根据玩家选择的范围判断是否越界，而不是根据事实条数判断。

总量预算可以使用可测量的字符或字节，再结合实际 provider 用量调节。没有必要为了这一轮把数字直接从六改成八。

同一次详细观察也不应仅为绕过容量限制拆成多次玩家行动、重复计时或重复调用。确需分块处理时，仍应属于同一观察及其时刻。

2. 观察结果需要容纳“可继续互动的内容”

这八条里，信封、衣物、门洞与气味、照明的后续作用并不相同。

我建议保持以下边界：

新的可互动物、通道或关键发现，由 KP 的世界补全或观察裁定明确建立。
这些内容可以在同一提交中登记，并被观察结果引用。
纯粹的表面质感可以由作者补充，并保留实际交付的原文。
作者不能因为结构化材料只有六个槽位，就自行补出第七个可拿走的物品或第八条线索。

不必给每片墙面纹理建立实体。一个尚未参与行动的普通陈设，可以先保留为稳定的环境事实；当玩家指向它时再增加交互精度。关键是它已经有被承诺过的存在依据，而不是后续每次重新生成。

“看见信封”也不自动包含“知道信封内容”。发现对象、识别对象、读取内容，应按实际选择与感知条件处理。

3. 首次报错就应准确，无需换入口获取答案

第 91 轮已经证明 place 与 output 的模型可见错误不一致。

不过，旧摘录中的 stageLocation 已有按 action 选择分支并提取字段错误的逻辑，因此不能直接说内核完全缺少这项能力。更可能是外层 union 校验先截住了请求，或不同入口使用了不同的错误投影；具体层次需要真实错误链确认。
source-excerpts

我会要求所有入口对同一问题给出一致的信息：

哪个操作；
哪个字段；
实际值或数量；
违反了什么限制；
当前批次是否执行；
哪些既有成功收据继续有效。

这属于契约与错误传播的收敛，不需要新加一个模型来解释错误。

五、我认可的整体地点与临时场景设计

前三个问题需要尽快处理，但长期目标仍应覆盖整个探索过程。

1. 临时性体现在来源和细节程度，不能体现在身份随时可丢

临时创建的旅馆可以只具备建筑、入口和前厅；二楼走廊、客房、窗户随后逐步补全。已经被使用、改变或明确观察过的部分，应继续保持身份与后果。

一次“探查门厅”的叙事场景结束，不应使门厅、信封或被打开的门重置。

我会持续区分：

持久空间：旅馆、前厅、走廊；
局部参照：柜台、窗边、左墙；
边界与通道：门、楼梯、通路；
叙事场景：这段交谈、探索或冲突；
持续事件：会跨时间、位置或视点延续的过程。

空间可以逐步细化，叙事焦点可以变化，实体身份不随之重建。

2. 移动应指向明确的最终位置，观察应从执行后的实际位置发生

我会继续保留“到达”与“聚焦观察”的区别，但减少模型需要维护的重复信息：

移动提交目的位置及必要路径。
宿主确定实际到达位置。
观察从该时刻的位置派生视点。
观察目标与观察者站位分别表达。
作者使用结算后的视点与结果。

已有窗口、门和路线能直接引用时，不应为了执行观察而重新定义一遍空间。

对于“门外看见门内插销”，目前应继续保留为质量疑点。需要看观察发生时门是否打开、玩家处于哪一侧、插销的位置和实际观察材料，才能判断。

我不会为这一个细节加专用规则，也不会每轮增加视觉事实复审模型。更有价值的是让重要的边界侧、门窗状态和感知路径进入本次裁定，随后通过真实样本评审剩余的语义误差。

3. 普通外观与可行动结构可以分层，但不能断开

普通场景描写交给作者，是合理的减负方向。与此同时，KP 至少要确立玩家接下来可以依赖的空间结构与发现。

例如首次进入一间餐馆：

入口、柜台、可见通路与主要相对位置，需要有稳定依据。
木料磨损、光线在桌面上的表现，可以交给作者。
“柜台后另有一扇可通行的门”会改变行动可能性，需要经过世界补全与感知裁定。

这种分工允许具体、丰富的场景演绎，同时避免为了文采生成一条未经确立的新出口。

4. 持续事件仍需要独立于观察的身份

本次五轮证明了所报告的视点和时钟一致性，尚未验证：

同一事件更换观察目标后是否仍保持身份；
参与者移动后事件是否被复制；
离开视野与事件结束是否区分；
NPC 自主追来是否有路线、时间和知识依据。

如果这些部分仍沿用此前“目标点＋名称复用 situation，并由 observe 更新阶段”的实现，它们仍值得调整。此前代码对这一风险有直接依据，但我不能仅凭旧摘录断言最新实现完全未变。
source-excerpts

目标保持不变：事件有自己的身份与演进依据，观察引用事件在某时刻的可感知表现。无需为此启动全城 NPC 模拟，也无需为每次看一眼都创建事件。

六、如果由我主导，正常执行会怎样组织

我会保留一个主要的地点动作入口；工具是否继续叫 place 并不重要。它背后的职责应是：

宿主提供可直接使用的上下文。 当前位置、相关已有对象引用、状态变化、必要来源，以及已成功的步骤。
KP解释玩家选择。 提出必要动作，以及确实缺少的对象或未知方面。
宿主完成引用绑定和结构预检。 新定义、既有补全、真实动作分别处理。
现有领域处理器按序结算。 继续使用同一事务底座和收据。
生成本轮观察与交付材料。 作者获得实际结果和可感知事实。

以第 90 轮为例，在条件已经明确时，一次提交可以表达：

部分	内容
既有引用	正门、钥匙、老宅
必要补全	模组或当前状态尚未登记的门厅区域及关联结构
有序动作	解锁 → 开门 → 跨门到达门厅 → 观察近处
结果	门的实际状态、玩家实际位置、耗时、观察证据

这里不要求“先生成门厅、再调用解锁、再读一次、再移动”的固定仪式。

如果钥匙是否适配、门后是否存在障碍，必须通过真实结果才能确定，就在该点处理未知。后续动作不能预先宣称成功。

这可以先用现有顺序命令与收据实现，不需要立刻引入完整的计划语言。 当前要解决的是重复表达和错误分派，不是新增任意条件、循环、依赖图或补偿脚本。

同时，place/apply/output 可以继续作为内部兼容入口，但同一个动作的参数语义、校验和错误应一致。模型不应为了知道事实条数超限而换一个工具，也不应为了获得后台平面图而模拟玩家看地图。

五轮干净成功的范围是 56.288—111.239 秒，这是有价值的正面证据，但样本不足以推断稳定达标率。第 90 轮有一次恢复，第 91 轮有四次工具错误；它们说明恢复路径昂贵，却不能仅凭总时间定量认定某个错误消耗了多少秒。
