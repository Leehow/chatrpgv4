## 最终结论

Pro 建议保留事务、收据、幂等、地点身份、最小内联创建和各领域处理器，并收敛它们上面的行动执行职责。

第一轮主张优先建立宿主持有的有序活动。收到补充证据后，它明确调整了近期次序：**先消除已确认的契约信息丢失，在信息完整的现有流程下建立基线，再决定活动层需要改到什么程度。** 不应把接线错误造成的时间问题全部算作大重构的收益。

## 近期先处理什么

已经只读复现一条确定性的接线缺陷：

1. `turnPacketParameterSchema` 把当前时间类别的 `covers` 写入根 `description`。
2. `locationCommandOwner` 用自己的根 `description` 覆盖它。
3. 结果是非地点 schema 有说明，经过地点投影或直接以 `locations=true` 生成后，该说明不在这条 schema 通道中。
4. 原回归只检查了非地点 schema，没有覆盖最终组合及 provider 请求。

该缺陷本轮未修。它不证明模型整个请求都看不到定义，也不证明 Jev 同样缺少说明，更不能直接解释 `until`、`minutes` 或所有历史时间失败。

Pro 建议恢复组合后的语义完整性，并验证非地点、投影后、直接地点模式、最终 provider 声明四端。应来自同一规则来源，避免反复拼接或复制一套提示词表。

随后保持模型、阈值及其他协议稳定，分别看提案生成、准入、执行排序与最终交付。若普通行动因此稳定，可以降低大规模活动层重构的近期紧迫性；若仍有系统性顺序/成本/恢复缺口，再收敛这些职责。

补充代码也让它更充分肯定当前 admission：已经一次打包选择/限制问题，具备批内条件位置、规范时钟、前序结果、逐行原话语境及 NPC 行动主体区分。因此，优化应整合现有能力，而不是另造平行机制。

## 整体架构仍需优化的方向

### 1. 行动、成本、进度和交付形成同一条可恢复记录

一条自然语言行动绑定目标、限制、有序步骤、成功收据、当前停点和待交付内容。普通成本绑定对应活动或步骤，重试不再重复计时。

宿主连续执行已知且已授权的步骤；在未知结果、真实障碍、重要事件或新选择处停下。最终 `output` 的单目的地形状不应决定物理行动必须如何切段。

原子事务仍是局部结算单位，整条行动可以有多个真实提交点。技术错误与游戏内失败区分。已执行但未交付的结果可以可信地部分交付并恢复，玩家应清楚自己实际在哪里、时间到哪里、哪些尚未做完。

首次意图绑定仍需确保没有漏掉“读菜单”等目标；执行器无法替错误理解后的计划证明玩家需求已完成。

### 2. 世界事件与观察证据分离

争吵应有独立事件身份、参与者、活动范围、阶段、已处理时刻、变化原因；不能以“目标空间点＋名称”承担长期事件身份。事件移到巷口、观察从门外换成窗边，仍可能是同一件事。

观察引用事件及状态版本，记录从何处何时感知到了什么。“看不到了”属于证据与认知，不等于世界中的事件结束或变成 unknown。

按相关事件边界稀疏推进，重复观察不重新抽世界；补算时间有明确区间。等待应允许在直接危险、目标失效或需要玩家重新选择的时刻中断，不能先扣完十五分钟再倒插第五分钟的关键决策。

### 3. 空间逐步细化，身份与视点保持稳定

内部关系宜使用稳定 ID，名字、译名、路径用于交流和检索。细化前厅或柜台后区域时，不重建原地点和物件身份。

不必做完整三维世界，但感知相关的位置差别应保留，例如窗内外、边界哪一侧、桌旁或桌下。当前感知点投影丢弃 `position.relation` 是有代码依据的风险；是否已造成特定实玩故障仍需证据。

已知路线和障碍由执行器绑定检查；模型遗漏 `through` 不应让门失效。由于未提供完整移动处理器，Pro 没有断言当前一定能这样绕过障碍。

### 4. 沉浸式描写成为下一轮可引用的经历

区分影响行动的结构、需要重访保持的外观、当次文字表达。来源没写与来源还没读取也要区分。

保存实际交付的外观及地点、视点、时间。玩家后来指认某把椅子，再依据原文把它提升成稳定锚点或物品；无需首次描写就结构化所有装饰。比喻、传闻和不确定外观不应升级为确定事实。

Pro 指出当前作者指导要求记录 `observe facts`，而最终作者没有这条写世界职责。这是职责冲突；不能仅凭此断言所有细节未保存，但“交付外观→下一轮稳定指认”的链路需要闭合。

### 5. 编译器区分纯定义与真实发生

真实移动、时间、观察、人物到场保持因果顺序。只有没有时间意义的身份定义可以安全前置。

当前 `walk_on` 编译后包含 NPC 放置，不只是分配身份。因此，即使最近修复了人数评估依赖，也不能把所有此类操作当纯定义随意重排。Pro 将其列为静态结构风险，没有宣称对应新例子已在原 App 发生。

### 6. 工具、Mod 与跨领域职责清晰

常用操作的小签名应完整，当前地点/规则/事件数据按需提供。入口过于开放、再靠查 contract 补齐，可能把上下文节省转化为错误修正成本；最终 `output` 也不宜再复制全部领域 schema。

Jev 用于必要的语义绑定、歧义、目标覆盖与额外承诺判断；已绑定步骤是否执行、时间是否重复、资源约束等由确定性逻辑证明。评审没有提供改动准入阈值的校准依据。

地点 Mod 保留，明确 requires/provides、写入权、覆盖策略及迁移所有权。禁用验收应检查能否继续离开已生成旅馆，不能只查旧记录能否读取。

NPC 跟随/追逐属于人物任务、知识、路线和时间的因果链；地点与观察提供空间及发现条件。背景群体可先保持群体，产生交互或持续后果再实例化。普通服务宜由服务领域拥有报价、交付/消费、时间与支付，不靠地点说明让 KP 每次手工编排增减物品。

## 后续验证应回答什么

- 相同自然行动一次说完和分次说，在没有新中断时产生相容的世界结果。
- 换视点不换事件身份，观察次数不无故改变事件轨迹。
- 改变家具、门、物品后离开重访，位置、持有和外观保持后果。
- 付款后、等待后、观察提交后或作者中断时，恢复不重复执行。
- 模组与新地点都能补全；已交付细节可再指认；升级、停用及重载仍可游玩。
- 分开确定性回归、真实模型理解和原 App 连续体验；记录真实 provider 用量、串并行时间线、修正次数和总成功率。
- 120秒仍按点击发送至正文完成的原定义；失败得快不能记成功，单次偶然通过不能代表稳定。
