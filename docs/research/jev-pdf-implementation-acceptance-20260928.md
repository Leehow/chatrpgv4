Thus a still-unrunnable waiter cannot suspend its lock holder; once claimed, foreground work still pauses background at the next provider boundary.

External cross-check: [Linux RT-mutex design](https://docs.kernel.org/locking/rt-mutex-design.html) and [FreeRTOS mutexes](https://freertos.org/Real-time-embedded-RTOS-mutexes.html) both describe allowing the lock holder to progress when a higher-priority task is blocked by it. Those systems use priority inheritance; this application has an existing claim scheduler rather than OS mutex priorities. The proportional fix is to leave pending-job ordering with that scheduler and prevent a second blanket pending-wait barrier. No real-time scheduling framework is added.
