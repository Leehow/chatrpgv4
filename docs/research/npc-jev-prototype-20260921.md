# NPC 性格与关系：Jev 原型实测

日期：2026-09-21。状态：固定情境的真实模型诊断完成；不是生产集成或真桌验收。

## 结论

这组小样本支持继续实现“稳定性格 + 具体关系经历 → 批量评价与反应选择”。差异确实进入了 Choice，而不只影响台词风格。不能从本实验推导完整 Keeper 回合会更快、更自然或更可靠。

可点击的[原型页面](../../.pi/prototypes/npc-jev/runs/run-HijuCm/prototype.html)是单文件 HTML，离线打开即可。页面切换的是实际测过的请求和返回；没有浏览器端密钥，没有对任意新输入伪造结果。可以切换性格、共同经历、可知范围、候选顺序与信息移除对照，并查看真实分数及生成样例。

实现位于 [experiments/npc-jev-prototype](../../experiments/npc-jev-prototype/README.md)，设计依据见 [NPC 方案](../specs/npc-personality-and-relationship.md)。正式内核、扩展、Mod 与战役均未修改。

## 2. 性格是否真的改变选择

三种人物面对同一份保管账本请求，场景、名字、既往关系和可用候选相同，只改变性格描述。

| 性格依据 | 完整材料：第一次 / 反转顺序复测 | 移除性格：第一次 / 反转顺序复测 |
| --- | --- | --- |
| 原则清楚，重视经手记录与可追溯性 | 登记封存 / 登记封存 | 登记封存 / 登记封存 |
| 温和谨慎，愿在可控范围私下相助 | 私下保管 / 私下保管 | 登记封存 / 登记封存 |
| 务实，承担额外责任前谈清回报与边界 | 谈条件 / 谈条件 | 登记封存 / 登记封存 |

可支持的判断：这三个明确而有区分度的人格描述，在本情境中改变了实际选择；删除描述后，三个请求收敛到同一种反应。

限制：候选是人工提供的，性格和场景的差异较鲜明，未证明模糊人格、多重动机或自动候选生成的质量。复测同时改变了候选顺序和调用次序，不能单独归因于某一种顺序效应。

## 3. 共同经历是否改变反应

同一位温和谨慎的人，面对同一项不交押金的借车请求：

| 共同经历 | Choice：第一次 / 复测 | “直接无押金借出”的关系契合度（0–4） |
| --- | --- | --- |
| 上次守约、提前还车并主动修轮轴 | 直接借出 / 直接借出 | 3.87 / 3.85 |
| 上次迟还三天、撒谎且未补偿 | 要押金或担保 / 要押金或担保 | 0.10 / 0.11 |
| 没有共同经历 | 直接借出 / 直接借出 | 1.58 / 1.33 |

删除失信经历后，两次都变为直接借出；删除守约经历的对照中，一次选择派人同行，一次选择直接借出。后者是保留的不稳定样本，不能概括成所有请求都稳定。

失信条件下的 Choice confidence 只有 0.38 / 0.57，但两次都选择增加担保条件，且多个限制合作的候选都可能合理。它提示：低 confidence 不应自动解释为“NPC 犹豫”或“一定选错”；也不宜现在设一个通用于所有 NPC 行为的阈值。

这些分数是当次证据契合度，不写入永久关系状态，不等于信任值或规则数值。

## 4. 可知范围、玩家中心与候选不足

完整上下文的 12 种输入各测两次，共 24 次，均落在事先定义的预期范围；12 对的最终选择在复测中一致。

- 确实见过封条时回答；没见过时坦诚不知道并建议询问。
- 玩家输入要求忽略限制、编出秘密时，仍选择不知道/询问。
- 玩家明确告别且无未完事项时自然结束，没有追赶或强加委托。
- “我不是来威胁你的……只问公开查阅手续”选择解释手续，没有把否定句当作正在威胁。
- 修车请求面对三个无关候选时，选择 `none`，交回 Keeper，而非强迫选一个。

知识隔离由宿主执行：显式 `knowers` 不含该 NPC 的事实先排除；依赖未知事实的候选也先排除。检查实际发出的 request，另一人的秘密标记和未知封条正文均未进入不应看到它们的请求。

因此，这部分首先证明原型输入投影按预期工作，不能写成“Jev 看到了所有秘密也不会泄漏”。当前样本也没有开放式知识获取或复杂传闻冲突，不能证明未来生产投影的完整性。

## 5. 选择能否形成可读的人物反应

第二个工具作者只收到相应人物视角和选中意图，写出了不同的帮助方式：

- 原则型要求登记接收、封存和经手记录。
- 重情型同意低调保管，并确认取回安排。
- 务实型先谈责任和保管费用。
- 面对守约者提到上次归还和修轮轴；面对失信者提到迟还及未了结的责任。
- 告别样例简短结束，没有追加任务。

主会话读过这些输出：反应基本符合输入与选择，没有宣称玩家已经接受条件或完成物品转移。它们仍是偏规整的短回复，本实验没有盲评、连续对话或与 Keeper-only 文本比较，不能宣称自然度已经提高。

## 6. 重逢补全

信息稀少的修表匠先由 Pi 生成一次“沉静细致、重视诚意与分寸、带克制幽默”的描述。第二个独立作者拿到的描述与保存文件逐字相同，没有再次生成人格。

它根据三天游戏时间、一次短雨和上次约定，写出重逢片段：她说店里这几天安静，怀表初步看过，还未维修、定价；邀请先听检查结果，再讨论下一步。输出把背景细节、人物自述和待玩家决定的提议分开。

这证明一次保存的人格能传给后续工具作者，并支持一次有约束的间隔补全。样例偏保守，尚未检验更丰富的生活变化、长间隔、冲突历史，或正式提交后再次重逢的一致性。没有构造三天期间的虚假事件流。

## 7. 时间、调用量与费用

| 指标 | 观察值 |
| --- | ---: |
| Jev 请求 | 34 / 34 返回完整结构 |
| 类型化小问题 | 430 |
| 两路并发的整个 Jev 批次 | 6.817 秒 |
| 单请求耗时中位数 | 375 ms |
| 单请求范围 | 300–785 ms |
| 输入 token | 91,422 |
| 输出 token | 8,834 |
| 按 adapter 当前价目估算的 Jev 输入费用 | 约 $0.00384 |

费用不是账单，不包含作者调用；作者 provider 的本地价目返回零，不能据此认为生成免费。两个成功作者任务分别花了约 33 秒和 41 秒，它们也不是生产中每回合必须增加的任务。

430 个问题共享若干输入，不是 430 个独立测试案例。样本不够建立可靠 p95。没有全回合基线，不能把 375 ms 叫作玩家一回合延迟，也不能从这组结果宣称整局提速。

## 8. Grok 两次失败的准确范围

最初使用 `xai/grok-4.6` 与 `grok-build/grok-4.6` 的两个工具作者尝试，均在工具调用前返回：`Service temporarily unavailable. The model did not respond to this request.` 没有明确的 401/403 证据。Pi 进程虽退出 0，消息的 `stopReason` 是 `error`，因此原型把它们判为失败并保留记录。

鉴权由原型设置的仓库 `.pi/coc-agent` 解析，分别使用其 `auth.json` 中两个 provider 的 OAuth 凭据。它们不是正在运行的 App 的 credential home。只读比较确认，App 使用的 `~/Library/Application Support/Pipi/pipicoc/pi-coc/agent/auth.json` 中，对应 access 与 refresh 均与源码目录不同；比较只输出是否相同，不输出 token。

所以结论只能是“两次源码配置下的原型请求失败”，不能说 PipiCOC App 的 Grok 不可用，也不能把两个 provider 名称当作两个独立服务故障。实际失败原因未定位，本原型不改动 App 凭据或服务配置。之后的性格/文本生成改用现有配置的工具型 Sol；Jev 测试使用用户本次授权的 key，二者凭据来源分开。

保留失败证据：[xai](../../.pi/prototypes/npc-jev/author-20260921/execution.json)、[grok-build](../../.pi/prototypes/npc-jev/author-build-20260921/execution.json)。

## 9. 页面和交付检查

已通过实际浏览器操作检查性格切换、移除性格对照、输入变化后隐藏旧建议、重逢片段显示。页面脚本通过语法检查。

截图操作超时，因此不声称截图视觉验收通过；DOM 操作证据与截图能力分开。页面的“请求变化”仅演示原型读版本失效，不证明正式 TaskRuntime 的事务或恢复行为。`host-diagnostics.json` 中的 JSON 往返等机械检查也不算生产持久化验收。

## 10. 下一步建议

1. 接入真实 NPC 材料与面向具体调查员的关系证据，先落实可知视角，再接语义判断。
2. 把候选供给作为独立质量问题：本次手写候选已经表明 Choice 能选，但还没证明真实 Keeper 能持续提供足够好的候选。
3. 将批量判断作为按需辅助，保留直接回答、自然结束和候选不足的出口；不在每句对白前强制增加一次生成加一次评分。
4. 先完成小范围正式路径与玩家体验验收，再推广。保留本实验的正面结果、对照不稳定和作者服务差异，不能用它关闭全部方案验收项。
