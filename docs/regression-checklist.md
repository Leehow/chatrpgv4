## 缺口清单

按真桌命中概率从高到低排列，只列上表「缺口」与「无测试但代码正确」两类：

1. **（#67）`apply damage` 不支持复合骰式，而内容本身就有复合骰式，且真实玩测已经在同一本模组上撞过一次。** `content/starters/the-haunting/module-graph.json` 里 Corbitt 一类怪物的伤害表达式含 `"1D3+1D4"`，`content/rulesets/coc7/rules-json/weapons.json` 里霰弹枪等武器也有 `"1D8+1D4"`/`"1D10+1D3"`。只要 KP 在无攻击者伤害路径（摔落、被同一击杀死后的追加叙述、任何绕开完整战斗会话的裸伤害）里报出这类表达式，`table.py::_stage_damage` 调 `percentile.roll_expression` 就会 `invalid_params` 拒绝。**最小修复**：让 `table.py::_stage_damage` 复用 `kernel/coc/rules/combat.py` 里已经支持复合表达式的 `_roll_damage_expr`（或把它的解析逻辑提到 `percentile.py` 供两处共用），再加一条 `tests/kernel/test_apply.py` 里的用例：`apply {kind:"damage", dice:"1D3+1D4"}` 应该成功而不是 `invalid_params`。

2. **（#68+#69）KP 输出的语言纯度——场景/手卡英文标签原样投给玩家、正文夹生英文单词——完全没有检查。** 这是新架构里唯一一类"存在过检查（旧树的 `mixed_language` 闸）、现在退回到零检查"的回归：`label` 校验只查非空不查语言（#68），`narrate` 的确定性核对只查数字不查语言、校验车道的三类 finding 里没有语言纯度这一类（#69）。**最小修复**：不要用正则/关键词去判断"这个词是不是不该出现的英文"（会撞到本仓库"语义问题不许硬编码"的红线），而是把它交给已经存在的 LLM 校验车道（contract §12.5）——给 `findings` 加一个 `kind: "off_language"`，让校验模型看一眼 `campaign.play_language` 与 `rendered_text`，判断是否有非声明语言的实词混入；`label` 这类结构化短字符串同样可以搭车验证（校验车道的输入已经拿到 `rendered_text`，`apply` 效果的 `label` 也在同一回合的收据里，一并喂给它）。这是 advisory 不阻塞交付，与 `warnings` 机制（§12.5）完全同构，不需要新的阻塞路径。

3. **（#65）昏迷/濒死角色在同一回合内被无限次攻击、玩家零输入的可能性仍未被结构性堵死。** 现状只是"建议升级"（Director `override: SUBSYSTEM`），没有硬阻断。**最小修复**：在 `resolve.py` 的 `_chase_slots`/combat 分支上加一条规则——当 `resolve` 的目标（`action.target` 或 `turn_of`）在**本回合**内已经进入 `dying`/`unconscious`/`dead` 且没有中间发生过 `ask`，同回合内对它的下一次 `resolve(intent: combat)` 报 `turn_state`，`fix` 提示「先用 `ask` 确认要不要继续，或改叙述为战斗结束」。这条比前两条更需要设计判断（怎么界定"同回合内的连续攻击"而不误伤正常的一场战斗多轮攻防），建议先写一条能复现旧 T36 场景的回归测试（NPC 对已 `unconscious` 的调查员再次 `resolve(intent: combat)`），再决定具体挡在哪一步。

4. **（#61）`kernel/coc/modules/evidence.py`/`bin/coc-evidence` 没有专门的单元测试。** 代码本身读起来是对的（`search`/`verify` 命令齐全，与契约描述一致），但 `grep -rln "coc_evidence\|evidence.py" tests/kernel/*.py` 找不到任何直接调用。**最小修复**：加一条 `tests/kernel/test_module_bind.py` 或新文件里的用例，构造一个小 packet，跑 `bin/coc-evidence search <name>` 与 `verify <span-id>`，断言输出命中/不命中，把它纳入现有的 packet/review 集成测试旁边。

5. **（#23）模组声明的 `start_time`（起始时刻）没有被发现写入 `world.json.clock` 的初值路径。** 优先级较低，因为 the-haunting 本身没有声明 `start_time`，现有测试测不出这条，真桌命中概率取决于以后哪本模组第一次声明它。**最小修复**：在 `campaign.create`（或建卡的 `create-campaign` 步）里，如果模组节点声明了 `start_time`，把它换算进 `world.clock.minutes` 的初值，并补一条断言「声明了 `start_time` 的模组建战役后 `where.clock.elapsed` 从声明的时刻起算，不从 0 起算」。**2026-09-06（#23）更新**：这一条还有个更早的坑已经修掉了——`capsule.clock_section` 读 `start_time` 用的是 `record_of(graph.module_node)`，而模组节点装的是 `documents` 不是 `record`，所以**就算模组声明了也读不到**（契约 §15.9）。现在四个读模组节点声明的地方都走 `module_graph.module_declaration`。写入 `world.clock` 初值这条仍然没做。

6. **（#11）预生成玩家卡不会被误分类为 NPC，这条只在契约层面（`node_kinds` 闭合枚举区分 `investigator-template`/`npc`）成立，没有专门的回归用例钉住它。** 优先级最低，因为触发它需要读者主动把预生成卡的 section 误分类，属于"模型判断错误"而非"代码结构漏洞"。**最小修复**（如果要做）：给 `module.plan.accept` 加一条用例，构造一个内容明显是玩家卡（`payload: character_sheet` 或同义标记）却被分类成 `kind: pregens` 之外的候选，断言后续 grounding/coverage 门至少不会把它当 `npc` 节点接受。
