# 按动作确定物品能力：统一身份与用法参数

## Problem Statement — 问题与成功标准

玩家希望说「我抄起场景里的椅子砸过去」，守秘人就能据实判断、补齐需要的参数并结算，而不是要求玩家先把椅子登记为武器。NPC 应遵守同一条路径。

当前物品增强能够生成武器定义并创建实例，但执行资格依赖物品定义的 `category`：只有 `weapon` 投影成可用武器。已有普通 `item` 定义不可重生成，托管实例又不能借普通物品授予路径重新登记。于是同一张椅子能不能砸人，取决于第一次登记时给了什么分类。

**用户已确认的方向：物品保存它是什么，动作决定这次怎么用，用法参数描述如何结算。** 物品分类不能替代动作语义判断；同一件物品不能因为用途变化而被复制、改名或重置。

成功是：纯场景道具、已托管普通物品和已有武器，都能由守秘人根据玩家/NPC实际行动选择合理用法；没有适用参数时生成，有时复用；在原行动内完成准备和结算，状态与收据真实一致。

空心交付包括：只把分类改名；只允许新建的「椅子武器」；参数卡能显示但战斗不用；每次攻击重新生成数值；生成要等玩家多说一句话；只证明内核 RPC 可调用，却声称自由行动体验已验收。

## Solution — 解决方案

实体物品保留统一实例身份。守秘人结合动作、场景和物理事实识别用法，带工具的 creator 补齐缺失的用法参数，内核通过现有规则执行器校验并结算。

以椅子为例：

1. 守秘人确认该椅子存在、可接触，以及玩家确实选择拿它攻击；必要的拾取仍有状态变更收据。
2. 选择「抡击」这一用法；如果同一张椅子已有适用的抡击参数，直接复用。
3. 没有适用参数时，creator 根据物理事实、规则依据与动作描述生成；内核接受后，仍由当前守秘人继续原行动。
4. `resolve` 使用这张椅子的该套参数结算。实际伤害归内核算，所有权和破损由真实状态变化承载。
5. 改成投掷时选择另一用法；拿来堵门时走相应普通行动，不因它曾伤人就强迫进入攻击。

玩家不手填参数、不选择内部分类，不必再说一句「请给它生成武器属性」。准备可能需要模型等待，但等待必须真实可见，不能伪装成攻击已经完成。

## User Stories — 用户故事

1. 作为玩家，我希望抄起尚未登记的场景物件攻击，以便临场行动不被物品目录限制。
2. 作为玩家，我希望已登记的普通物品也能临时用于攻击，以便最初的分类不决定后续用途。
3. 作为玩家，我希望同一物品有不同用法，以便抡击与投掷使用各自适用的技能和参数。
4. 作为玩家，我希望同物同用法复用已接受参数，以便不会因换一句话而获得不同伤害。
5. 作为玩家，我希望拾取、转交和丢弃都作用于同一实例，以便背包里不会多出一件「武器版」复制品。
6. 作为玩家，我希望损坏、弹药、次数和容器关系持续有效，以便改变用途不能变相修复或补充物品。
7. 作为玩家，我希望物理状态真正变化后重新判断适用用法，以便断椅仍可被合理使用，但不继续套完整椅子的旧参数。
8. 作为玩家，我希望不造成伤害的动作仍按其本意处理，以便拿椅子堵门不会自动变成攻击或消耗战斗动作。
9. 作为玩家，我希望不合理的用法得到符合事实的处理，以便「我想这样做」不会凭空赋予物品能力。
10. 作为玩家，我希望一次已表达清楚的行动能在参数准备后继续，以便不必为系统登记再补一句无意义输入。
11. 作为守秘人，我希望看见物品已有用法、适用条件与缺失参数，以便选用已有能力而不是每回合重建。
12. 作为守秘人，我希望 NPC 与调查员采用同一物品用法链路，以便临时拿物攻击和转手后使用的规则一致。
13. 作为守秘人，我希望在已开启的战斗中也能切换用法，以便参数不是只在开战时生效。
14. 作为玩家，我希望中断、重试和重启不会重复拾取、重复投骰或重复扣资源，以便系统等待不会改变战斗结果。
15. 作为已有战役的玩家，我希望现有武器、普通物品、文档和消耗品继续可用，以便升级不重算既有资产。
16. 作为玩家，我希望关闭生成 Mod 后仍能使用已接受的用法，以便停用生成器不删除已经存在的能力。

## Implementation Decisions — 实现决定

以下为本规格选定的实现方向，不是当前接口清单。

### 1. 三个概念分开，不增加一套物品系统

- **物品定义**保存已经接受的来源、说明、物理事实与既有能力数据；保持原定义的不变性。
- **物品实例**保存持续身份及真实状态。用途变化不更换实例，也不重建所有权、弹药、次数或文档。
- **用法参数**是附着于实例、带适用依据的不可变记录；同一实例可有多套记录。首期按实例复用，不引入跨物品或跨战役的全局生成缓存。

物理物品的 `item` / `weapon` 不再作为执行资格。新实体无需被划入互斥的普通物品/武器类型；兼容层可以保留旧 `category` 字段和展示标签，但执行器读取能力而不是该标签。伤害字段不是「武器身份证」。

咒语知识不是实体物品，本次不合并 `spell` 与物品，不改变持有书籍不等于学会咒语的边界。现有文档、容器、消耗品等能力继续存在，不能因新增攻击用法被覆盖。

### 2. 开放语义交给守秘人，执行器保持闭合

守秘人根据实际行动选择用法，判断物件是否可得、物理上是否合理、是否与既有用法等价。这里不新增每动作一条独立语义车道，不写物品名列表、关键词路由或名称到伤害的映射。

creator 仍是带 `read/write/edit/bash` 的 Pi agent：读当前事实、已有用法、规则与预设，准备参数及依据；不能改写模组真相，不能从未公开线索推导玩家可用的新事实，不能把玩家意愿当成物理事实。

内核仅接受已登记的执行能力、闭合字段和有效参数。首期完整打通已有攻击结算所需的近战与投掷用法，包括命中技能、伤害表达式、适用距离、每轮使用限制、贯穿及伤害加值规则；不接受只有 `damage` 的残缺档案。具体数值不在本规格预写，由来源、规则与经过校验的生成结果确定。

伤害表达式是参数，伤害结果必须由 `resolve` 计算。有攻击者的伤害不能绕到环境伤害 `apply damage`，也不能用 `note` 或叙述代替结算。

非攻击用途继续通过已有普通检定、物理事实与 `apply` 表达；本次不新建承重、堵门、建筑破坏等物理执行器。遇到现有执行能力无法表达的机制，明确报告缺口，不生成一个无人执行的字段。

### 3. 保留七个动词，追加用法登记与选择

在现有 `apply` 效果族中增加 `usage`：用实例自然名、用法自然名和动作描述请求准备/登记用法；数值草稿由宿主私有字段携带，不让守秘人抄内部 id 或提交未经接受的执行参数。

物件还未实例化时，已有 `define` / `object` 与 `usage` 可以在同一批表达。事务先在暂存视图中解析定义、实例和用法的依赖，再整批校验写入。已有托管物品只追加用法，不重新 `define`；已有未托管装备通过现有认领路径转成同一资产的实例表示，不再授予一份。

`resolve` 增加可选 `action.usage`，用实例自然名加用法自然名确定所选能力。`action.object` 是统一实体入口；现有 `action.weapon` 作为攻击兼容入口继续有效。两者同时填写而指向不同物件时拒绝，不静默择一。

单一适用的默认攻击用法可以省略选择；多个适用用法不得由内核猜测，返回给守秘人已有用法及所需选择。玩家已明确说出抡击/投掷时由守秘人选择，不强迫玩家再选择内部术语。

未登记、已失效、未持有或参数未就绪时，拒绝发生在投骰及资源变化之前，给出可修复原因。默认攻击仍不覆盖 `objects:use`、`objects:repair` 或咒语决策。

复用 `mods.job`、`mods.accept` 与已有 Mod 准备通道，为用法增加明确的输入/结果类型和能力协商；它不是重生成旧定义的旁门，也不把 creator 放进叙述后的提交链。

### 4. 持久记录与参数复用

每条接受记录至少包含：宿主铸造的标识、所属实例、用法名、受支持执行能力、参数、适用物理依据、规则/执行能力版本、生成来源与接受状态。旧记录保留，不在原位覆盖数值。

同一实例、同一既有用法、相同适用物理依据和兼容规则版本，应直接复用，不新开 creator。语义等价的不同说法由守秘人选择同一用法；不把玩家原句或每回合全文哈希当作复用键。

宿主以规范化的物理依据和规则版本判断缓存新鲜度，键和内部引用不暴露给模型。实例换主人、回合变化或描述换一种语言不是失效原因。行动者技能值、伤害加值、当前距离、目标防御、弹药和剩余次数在执行时取当前值，不缓存为一次生成的永久结果。

材料、结构、完整性等相关事实改变后，旧记录仍可追溯但不能未经检查继续执行。守秘人可以选择仍适用的既有用法，或为改变后的状态请求新记录；不能让 creator 通过更改依据宣称物品已修复。

`jammed` / `broken` 不再对所有用法一刀切：卡壳枪不能射击，但可能还能敲击；断椅不能无条件沿用完整椅子的抡击参数，但可以据现有残存结构生成适用用法。这不是清除状态，也不是默认破损物仍然可用。

弹药、次数与数量只在实例的权威状态保存；多套用法不得分别克隆一个弹匣或次数池。批量普通物品若不能无歧义地指向其中一件，使用现有数量/持有约束明确拒绝，不在本次偷偷新增拆堆系统。

### 5. 当前行动所需参数不能等下一回合

现有「仅定义与认领」批次可以后台登记、下一回合接回，这是开场装备补全的优化，不是攻击准备协议。

本次新增的 `usage`，以及同批中它依赖的定义/实例，必须走当前行动依赖路径：参数接受之前不执行攻击、不交付已成功攻击的正文，也不能要求玩家追加输入才能接回结果。已在后台准备的同一对象复用在途任务，不开第二次生成。

正常完成时，宿主把结果交还仍在处理该行动的守秘人，由它继续原 `resolve`。准备超时、取消或宿主重启时，保留任务证据与明确待处理状态，不伪造成功、不盲目重发攻击。恢复只能关联仍有效的原行动；过期结果不得影响另一回合、世界线或已换状态的实例。

准备、接受和动作执行是不同阶段：准备结果不等于物品已取得，登记成功不等于攻击已结算。不得把跨多个工具调用的链路宣称为单个数据库事务；每次 `apply` 保持整批原子，`resolve` 保持自身幂等。如果拾取已单独提交而后续失败，收据必须如实显示物品已取得而攻击未发生，不再拾取一次。

### 6. 行动准入与玩家/NPC对称

能力存在不等于行动获准。玩家的原动作必须在生成开销和变更之前经过适用的宿主准入：明确选择「拿椅子攻击」可以覆盖必要准备；只是提及或查看椅子，不授权拾取、投掷或攻击。

现有 `define` / `object` 被视作记账的豁免，不能被本链路用来绕过真实拾取/转移的准入。规格要求把「纯参数补全」与「动作所需物理变更」区分在结构化协议中；内核不靠解析理由文字决定豁免。纯用法登记不推进时间、不花动作、不改 HP、不消耗弹药。

NPC 的意图由守秘人按既有 NPC 主动行为规则决定，不伪造玩家输入；持有者、实例状态、用法适用性、战斗顺序与资源约束同样必须校验。新用法不额外授予一个行动，不绕过正在等待的防御选择，也不自动替换战斗目标。

### 7. 投影与战斗读取同一份能力

物品查看、调查员表、NPC 武器选择和已开启的战斗快照均从接受的用法记录投影，不再只筛 `category === weapon`。没有适用攻击用法的物品不凭分类获得攻击资格。

战斗中的用法身份必须能区分同一物体的抡击与投掷，物理资源身份仍指向同一实例。内部用法句柄由宿主/内核铸造，不能靠把实例改名成「椅子-抡击」制造一件新物品。

切换用法时刷新命中技能、伤害、距离与使用限制，不沿用开战时的旧档案，也不重开战斗或清空轮次。用法参数中的技能接入实际命中计算，不能只显示在卡面，不能假定填写 `action.skill` 就已覆盖战斗入口。

投掷完的物品必须以现有 `apply object` 转移/落地收据反映不再持有；再次使用前需要真实取回，不能只结算伤害而让椅子永远留在手里。跨调用的中断恢复沿用提交链，不能重复投掷或凭空回收。

### 8. 三端清单：写入、读到、据此行动

| 数据 | 谁写 | 谁读 | 谁据此行动及证据 |
| --- | --- | --- | --- |
| 用法参数与接受依据 | creator 准备；内核经 `apply usage` 接受 | `look`、Mod 上下文、能力投影、战斗解析 | 守秘人按名字选用；登记结果及攻击收据可关联同一实例与用法 |
| 所有权、状态、弹药/次数 | 既有 `apply object` 与规则结算 | 所有用法共用的实例视图与执行守卫 | 拾取/转交/破损收据、结算资源变化，不复制资源池 |
| 新鲜度与待准备状态 | 宿主任务通道及事实变更后的验证 | 当前行动的工具返回、恢复入口 | 守秘人等待、修正或续接原动作；未就绪没有投骰/成功结果 |
| 已有用法及适用限制 | 内核由已接受记录投影 | 物品查看与决策相关上下文 | 守秘人复用而非再生成；遥测能区分命中缓存、准备与实际选择 |

用法投影包含这行能力的使用条件与结算参数，不让守秘人跨多个来源拼装。参数和机制走结构化 JSON；玩家可见文字沿既有 `play_language` 生成/投影路径，不新增语言表。

offer 账只观测，不把「还没用过的能力」反馈成下回合义务。本次不增加物品评分、催促或使用次数配额。

### 9. 兼容、版本与 Mod 边界

现有已接受武器档案可确定性地视为默认攻击用法，保留原参数、实例和来源，不调用模型重算。旧普通物品继续存在，需要攻击能力时再追加用法。旧 `apply item.weapon` 仍支持规则表档案，不为兼容强迫所有历史装备立即迁移。

兼容读取可以识别旧分类以映射旧数据，但新执行路径不能继续用该分类做权限门。已有非托管武器行在没有明确认领关联时保留，不能为切换一个用法清空整张武器表；迁移后同一资产也不能产生两份可消耗资源。

新增记录纳入正常战役保存、重启、世界线快照和冲突处理；不回写历史定义、收据或玩测证据，不批量改旧战役。迁移需要在副本上可验证，正式升级遵守既有安全边界和战役版本锁。

核心拥有用法校验、状态与执行；Enhanced Items 拥有语义生成指令和预设。开启相应能力的新版 Mod 才新增生成；关闭生成器后，已接受且仍适用的记录继续可执行，缺参数时显式说明无法生成，不能回退为任意伤害。旧规则表能力仍按原兼容路径可用。

发布时新增能力声明并检查宿主支持，更新 Mod 版本和变更说明；不把同一已发布版本换成不同字节，不擅自升级已有战役的锁。

## Testing Decisions — 测试决定

### 验收接口

主接口采用现有宿主七动词到 TypeScript 内核 RPC 的完整路径：观察工具返回、收据、战役快照和物品/战斗投影。内核 RPC 用例证明状态及算术；宿主 Mod/准入接线用例证明实际参数准备与同回合续接。只在隔离生成延迟、取消和重试时注入受控 creator，不拿受控输出证明模型语义正确。

不另造测试专用战斗执行器。测试不能只断言内部 map 多了一条记录，必须证明那条记录被正确选择并改变实际结算所使用的参数。

### 必须覆盖的行为

| 场景 | 可观察断言 |
| --- | --- |
| 场景道具首次拾取并攻击 | 只生成一个实例；登记后在同一玩家行动内真实进入攻击；没有第二句输入要求 |
| 已是普通 `item` 的椅子 | 原定义及实例身份不变；新增适用用法；不再被分类拒绝 |
| 同一椅子抡击与投掷 | 命中技能、伤害和距离来自所选用法；资源仍属于同一实例；投掷后不再持有 |
| 再次使用与改写动作措辞 | 守秘人选择同一已接受用法后，生成调用增量为零，参数不漂移 |
| NPC先使用再转给调查员 | 同一参数与物理实例延续，技能/伤害加值按新行动者计算 |
| 活跃战斗中切换用法 | 不重置轮次/行动顺序，快照读取新用法而非首次装备缓存 |
| 状态变化 | 旧依据失效时不投骰；受损/卡壳不被换用法清除；只放行已接受且适用的另一用法 |
| 资源与容器 | 无第二弹匣/次数池；容器内或他人持有时不能直接攻击；改用法不补资源 |
| 仅查看、仅登记、无授权攻击 | 无未选拾取/转移/伤害；准入拒绝先于昂贵生成和效果写入 |
| 重复调用、失败、取消、重启 | 不重复生成或结算；过期结果不提交；已单独完成的拾取不会再授予一件 |
| 缺失或非法参数 | 只有 damage、不支持的技能/效果、越界骰式、歧义名称均不产生部分状态变化 |
| 旧档及 Mod 关闭/升级 | 旧武器结果保持；文档/消耗品/咒语不回归；已接受用法不依赖生成器继续在线 |
| 世界线 | 用法与实例随线保存，同一记录冲突显式处置，不静默复生成取胜 |

### 真桌验收

最终体验必须按项目唯一方法：`tests/play/driver.py` 以 RPC 模式启动 `bin/pi-coc`，建卡用 `bin/pi-coc-setup`；Grok 做守秘人，主会话做唯一玩家，一次一句自然输入，从建卡/开场到结局或真实阻断。

沿正常推进观察即兴攻击、同物异用、参数复用、状态变化与 NPC 使用；不预写玩家脚本、不造场景刷回合，不把 RPC 单测叫真桌。未在局中实际出现的能力点逐项记为未验证，不用确定性测试代替体验结论。

证据保留完整战役、模组、逐字记录、事件与遥测。记录首次准备耗时、复用时是否额外生成、动作是否同回合续接及实际使用的参数；不以回合数或报告篇幅充当成功指标。

## Out of Scope — 不做什么

- 不增加第八个守秘人工具，不创建第二套 Keeper、规则引擎或物理模拟器。
- 不做椅子/酒瓶/砖头名称白名单，不预置所有物品的伤害，不用正则判断用途。
- 不做制造、拆解、拆堆、碎片产出或自动耐久损耗系统；同一残存实体的状态变化可处理，真正拆出多件物品留给独立需求。
- 不增加新的堵门、承重、建筑破坏、毒物或法术执行器；不把所有非战斗机制重写成用法系统。
- 不做跨物品、跨战役的语义缓存，不做每次动作一条新语义审查车道。
- 不重做库存 UI、不让玩家编辑伤害参数，不在本任务打包或安装 App。
- 不恢复 Python 内核，不改历史对照、旧存档证据或已发布 Mod 包字节。
