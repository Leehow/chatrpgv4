# Turn IR：KP 只做语义决定，登记和执行顺序交给宿主

Status: 用户 2026-10-25 定案（修正版）。实现中。第一版设计稿经 ChatGPT（GPT-6）评审后修正，
评审原文与对照见 `.tmp/codex-play/chatgpt-event-packet-review.md`、
`.tmp/codex-play/chatgpt-review-vs-design.md`。

用户的三项决定：
1. 按修正版做：Turn IR 八个动作族 + 宿主执行协调器；名字只用来查，不当身份。
2. 第一阶段把检定（D 类）一起改：检定前固定目标与成功范围，宿主管检定屏障。
3. 同时跑一组对照：旧协议（v4）不变，只优化胶囊和收据的展示。

## 问题

Codex 逐段读了 9 局长局里 330 段超过 1k token 的 KP thinking（只做概括）：

| 类别 | 估算 token 占比 | 典型卡点 |
|---|---:|---|
| A 登记、引用与交付怎么装 | 29.6% | 人走 apply、walk_on 还是 new_N；发现走 clue、observe、reveal 还是 exhibit；fact_ref 给谁用；knowledge_status 选哪个 topic；正文谁写 |
| D 检定适用与结果重审 | 24.8% | 收据出来了还重判；可选续接当义务；复合目标失败后拆目标 |
| C 跨阶段执行顺序 | 22.8% | apply 立即生效、output 回合末生效；一回合跨几个地点要手工排序 |
| E 人物与因果演绎 | 10.2% | 正常思考 |
| B 查书何时收手 | 7.3% | 未命中、未读到、书里没写分不清 |
| F 被拒后整轮重想 | 5.4% | 小拒绝触发整条计划重写 |

根因：同一件故事里的事有好几种合法写法，选哪种要靠 KP 推理；而且两条写入路径的生效时点不同。

## 原则

**程序可以决定一件已经说清的事怎么登记，不能替 KP 决定这件事是什么意思。**

- KP 交 **TurnAction**（请求），内核给 **Receipt**（已提交的事）。两者不混用。
- 名字用来查人，不当身份。唯一匹配才绑定，冲突就返回带来源的候选。
- 提到一个人不等于他进场；说了不等于是真的；听见不等于信了；看到不等于读完。
- 去重的是状态写入，不是人物的表达行为。

## Turn IR：八个动作族

KP 每轮交一张按发生顺序排的 `actions` 表。人、地点、物件用名字或桌上称呼；同一张表里新建的
人可以用 `@别名` 指代（如 `@警员`）。KP 不写 `npc_N`、`new_N`、slot、`fact_N`。

| op | 表达什么 | 程序不许猜的 |
|---|---|---|
| `move` | 哪些主体移动到哪里（`actors` 明确列出；`inside` 表示新地点在哪个地点里；`via`） | 别的人是否跟着 |
| `presence` | 某人进入或离开哪个场景（`enter` / `leave`），可带公开称呼 | 被提到就算在场 |
| `communicate` | 谁对谁、通过什么渠道（in_person / phone / letter / aside）、做什么（沿用现有 act 集合）、说了哪些 `kN` 或 `{claim}`、`doesnt_know` / `wont_say` | 主张即事实、听见即相信 |
| `perceive` | 谁获得了什么感知：`kN` 或一句观察 | 检定成败、没读到的内容 |
| `material` | 物件和文件：`show` / `transfer` / `take` / `open` / `close`，`access`：glimpse / inspect / read_part / read_full | 看过就懂全文；持有等于知道 |
| `time` | 明确的时间推进：分钟、到几点、规则时段 | 重复计算移动和交谈的耗时 |
| `relationship` | 真实发生的关系变化（disposition、trust、fear、pressure、control），只写变了的字段 | 从语气推出数值、从情绪推出控制 |
| `rule` | 调用内核已注册的封闭规则操作（检定、战斗、追逐、治疗、施法），带固定的目标、难度、成功范围，`as` 给结果起名 | 擅自判定成功、伤害或权限 |

另有三个不改世界的小字段：`mood`（此刻的情绪表达，给作者）、`learn_alias`（调查员听到一个
称呼；确认真实身份要证据，走 `identify`）、`ambience`（光线、气氛，只给作者）。

`kN` 只是 KP 看到的统一编号；内部照旧分开存世界命题、出处与材料、NPC 信念、交流事件、感知。

### 检定屏障

`rule` 动作在表里就是一道屏障：宿主先提交它之前的动作段，再交规则内核结算，拿到权威收据。
屏障后的动作可以带 `when: {receipt: "r1", passed: true|false}`，只有两种，不做通用条件脚本。
满足条件的动作照常执行，不满足的丢弃并在收据里说明。检定之后需要创造性判断（NPC 怎么反应）
时，宿主把收据交回 KP，KP 再交下一张表。

检定前固定：谁、用什么技能、目标是什么、成功意味着什么、失败意味着什么（§268.1 的 stake）。
检定后不许重新解释已失败的目标。孤注一掷和幸运只由玩家声明（§268.6）。

## 宿主执行协调器

| 阶段 | 做什么 | 写入 |
|---|---|---|
| Bind | 绑定人、地点、物件、`kN`；`@别名` 在本段内有效 | 否 |
| Validate | 在模拟状态上按顺序检查每个动作的前提（在场、持有、可达、规则前提） | 否 |
| Commit | 把一段已验证的动作展开成现有内核命令，原子提交 | 是 |
| Receipt | 返回已提交的事、新生成的引用、被丢弃的条件动作 | 否 |
| Continue | 检定屏障后，按收据继续执行剩余动作 | 仅新的合法段 |

- 无屏障时整张表一个原子事务。有屏障时，已提交的前段不回滚，后段引用前段收据和检定收据。
- 每段带 turn_id、segment_id、幂等键、预期世界版本。复用内核现有的事务、收据和幂等重放，
  不在宿主里另写一套地点或物件状态机。
- 拒绝指到具体那条动作：下标、哪个名字、缺什么、候选；附已提交和未提交清单。修正只重交未提交的后段。

## 名字绑定

- 三类来源分开：`existing`（桌上已有身份）、`module`（书里的人，未必在场）、`new`（本表明确新建）。
- 唯一匹配自动绑定；同名、书名与桌上称呼冲突、假名都返回带来源的候选，让 KP 改写。
- 只有 `presence enter` 让人进场。`communicate` 走 phone 或 letter 时不要求同地，也不让人进场。
- 匹配只做精确名、书中印的名字、已登记的称呼和别名，不做关键词或语义猜测。

## 对照组：旧协议只优化展示

v4 写入协议一个字不改，只改 KP 每轮看到的东西：
- 在场的人各自唯一可用的引用，以及他此刻能说的 fact / source / exhibit。
- 调查员已知的事、手里的东西；物件和文件现在在谁手上。
- 本轮已掷检定的权威结果（目标、等级、成败、stake），以及接下来允许做什么。
- 不再常驻整套底层登记协议的长说明。

## 验收

- 回归覆盖：同名 NPC、假名、电话那头的人、NPC 说谎、只看一部分文件、检定失败、到达后检定、
  分头行动、战斗或追逐中断、前段已提交后段被拒；另加开场、跨日等待、SAN 首次遭遇、同一物件
  重复交接、谜题答案和信件原文不被作者改写。
- 等价性：固定初始状态和随机数，比较最终可观察语义（位置、持有、知识可见性、时间、检定、
  交付、出处），不比命令序列。
- 实测指标：每轮端到端等待（均值和 P90）、KP thinking token（总量、P50、P90、按类别）、
  KP 调用次数和每次的耗时、输入输出 token、首 token 延迟、工具耗时、拒绝数、状态错误。
- 成功：A 类长 thinking 至少减半；每轮 KP 调用中位数不超过 3；平均等待朝 60 秒走；
  拒绝数和状态错误不升。
- 空心交付：只改措辞、只加别名、只换字段名，或者为了数字好看减少玩家动作的种类。
