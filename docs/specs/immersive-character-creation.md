# 模组感知的沉浸式建卡与完整角色确认

状态：已实施并完成验收；本变更整合至 `0.9.0a`。
适用：pi-coc 0.9.0a，Electron 与同一 Pi setup 运行时。
工作分支：`codex/guided-character-creation`。
依据：本次用户逐轮更正、规则书原文、旧版实际调用链，以及真实浏览器存档。

## 1. 用户意图与成功标准

玩家选择模组后，立即进入一个符合模组的建卡场景。场景中的人物自然询问身份，玩家用一句话介绍自己；模型据此补齐人物，内核算出完整角色参数。玩家在确认之前就能看到实际角色卡，可以用自然语言修改。确认后，这张卡成为正式角色，故事从刚才的场景继续。

成功同时满足五项：

1. **有代入感**：建卡是一次世界内的会面、介绍或登记，不是模组简介后接问卷。
2. **少输入而有追问**：姓名、职业概念开启建卡对话；玩家未明确代劳时，先以一个入戏追问（有承重缺口才两个）引导玩家补完设定，再产生完整草稿；明确“其余你定”仍一次出草稿。逐项采访年龄、装备、亲属等普通信息仍然禁止。
3. **角色完整**：属性、技能、财务、装备、背景等进入对应的结构化字段，可被游玩系统使用。
4. **确认有对象**：展示的参数属于实际待提交草稿，确认后不能重新生成另一张卡。
5. **自然继续**：已发生的会面不重复，普通剧情通过玩家自由描述行动推进。

以下是空心交付，不得算验收通过：只有气氛散文；只有确认口头概念；确认之后才首次生成属性；角色字段很多但技能未分完；物品只在散文里；页面进入游戏就宣称完整建卡成功。

## 4. 玩家体验

### 4.1 模组选择后的代入场景

- 引导者优先使用模组已知且开场可接触的人物，身份与行为受 player-safe 来源约束。
- 用少量环境、道具、动作建立会面。
- 会面先把「这是什么」说明白：引导者用自己的话说清公开前提（他是谁、为什么见你），再自然问起来者身份与营生；旁白不写「报上姓名」一类打字提示，也不出现草稿、确认等元词汇——人物的问题本身就是给玩家的提示。
- 不显示职业建议卡片，不让玩家填写人物表单，不把一串剧情选项当作开场。
- 不因桌面语言为中文就推定角色族裔或姓名文化。

以 The Haunting 为语气示例，以下不是旧版引文或新设模组事实：

> 诺特把文件拢到一旁，示意你坐下，钢笔停在纸面上。
>
> “我是科尔比街那栋房子的主人。房子的事你也听说了——我需要一个信得过的人替我去看看。在这之前，我该怎么称呼你？平日做哪一行？”

具体环境、台词、职业建议与进入缘由由模型根据模组生成，不将这个例子硬编码为通用模板。

### 4.2 介绍之后：先入戏追问，再生成完整草稿

- 玩家给出姓名与职业概念、但没有明确把其余交出时，当回合不出草稿：以守秘人口吻提**一个**入戏追问（第一问答完仍有承重缺口才允许第二个），**问完等回答**。这一问花在真正改变卡面的东西上——只有玩家能定的**能力方向**：这人明显擅长或不擅长什么（眼尖、手稳、跑得快、会救人），用戏里的话问，绝不问数值；答桉落成具体技能方向。卷入方式、人际关系与关键联系、年龄、装备这类守秘人能合理拟出的一律不作追问，作为可修改的建议进草稿；追问结尾要告诉玩家接下来就出完整草稿。
- 玩家答完追问（或表示不再补充），生成完整草稿；仍未提及的普通缺项作为可修改的建议补齐。
- 玩家明确“其余你定”时不再追问，同一回合出完整草稿。
- 最多一个澄清，仅用于玩家设定与模组明确硬要求冲突、无法形成合法草稿的情况；缺年龄等可默认信息不算阻断。
- 玩家已经指定的事实不可覆盖、重问或随重试重生成。
- 生成过程中可以简短衔接场景，不伪造“剧情正在发生”掩饰等待，也不要求玩家执行命令。

### 4.3 展示完整参数并确认

草稿生成后，在当前建卡对话中自动展示完整、可读的角色卡。玩家不必在游戏开始后自行打开侧栏寻找结果。

必须可检查：

- 姓名、职业、时代、年龄等身份信息。
- 八项属性及当前规则要求的半值/五分之一值；HP、MP、SAN、Luck、MOV、DB、Build 等派生值。
- 最终技能值、具体专业和语言、职业与兴趣分配结果、信用评级。
- 现金、资产、消费水平与适用时代。
- 结构化背景、关键联系、模组卷入方式。
- 实际装备；有武器时展示其规则资料，未选武器可为空。

数字与规则参数仍走结构化 JSON 和专用展示，不为了恢复参数预览而取消当前机制投影契约。叙事正文负责人物与会面，角色卡负责准确数值。源数据同一份，避免散文先报一套、卡片生成另一套。

默认仅需要一次确认：玩家看完实际草稿后，可自然语言确认或提出修改。不把“生成”和“确认”强拆成额外两轮。角色预览是结果展示，不是重新填表。

若玩家明确要求“其余你定，直接创建”，视为委托生成并写入，可同轮展示最终卡并提交，免去额外确认；不能从普通自我介绍、玩笑或含糊回应推断这种授权。明确要求“先给我看，不要写”则必须停在草稿。

### 4.4 修改

- 自然语言修改由模型解释为结构化改动；不以关键词、正则识别意图或确认。
- 对已明确指定的修改重新计算受影响部分，展示更新后的实际卡。
- 未涉及的随机结果与玩家设定保持不变，不借“重新生成”偷换整张卡。
- 默认修改后确认最新草稿；若玩家明确说“按这些修改正式创建”，可依据这项明确授权提交更新结果，并完整展示。

## 5. 角色完整性

完整性由所选建卡方法决定，不由“party 有文件”“字段计数很多”或模型说已完成决定。

| 项目 | 完成要求 |
| --- | --- |
| 属性与派生值 | 由规则内核计算，年龄修正与骰子来源可追溯，展示值等于提交值 |
| 职业技能 | 选择型条目已经解析为具体技能/专业，所用方法的分配约束通过 |
| 兴趣技能 | 模型根据人物语义选择方向，内核完成计算；不机械地把点数撒给所有技能 |
| 预算 | 规则要求分配的点数完成分配；不存在未解决的 `choices_pending` 或未解释的保留点数 |
| 语言 | 具体语种落入结构化语义信息和需要的技能专业；不会某语种的明确限制得到保留 |
| 背景 | 使用旧版已有的对应背景字段；适用的前六类中形成 3–6 条有内容的线索，并有关键联系；不强行预设伤痕、疯狂或神话遭遇 |
| 卷入方式 | 关联当前模组具体公开开场；不得默认已经接受委托或获得物品 |
| 装备 | 已确认的重要随身物进入装备数据；武器有必要的规则引用；人物散文不是库存 |
| 财务 | 按时代、信用评级和所选方法生成；缺失规则资料要明确阻断或依契约报告，不能编数字 |

任何必需项不完整时，允许保存草稿与错误证据，但不能提交正式角色或标记 `ready_for_table`。应先由模型与内核解决可自行补齐的缺项，而不是把内部字段错误逐项抛给玩家。

## 6. 现有 setup 内的草稿与提交契约

只扩展现有 setup、建卡计算和战役状态，不新增一套建卡 agent、独立聊天历史或新的规则引擎。

### 6.1 职责

- **模组读者**：生成并复核可复用的场景和建卡材料。
- **现有 setup agent**：人物语义、对话、技能方向和装备选择、理解修改与确认。
- **现有 Python 内核**：规则计算、完整性校验、草稿保存、版本验证、正式提交。
- **宿主和 Electron**：将实际草稿投影到对话内角色预览，绑定所展示版本，保持会话恢复和幂等。

### 6.2 建议接口形状

以下方法名是本 spec 的实施提案；进入实现前须在 `docs/kernel-rpc.md` 同步正式 schema 和“内核的决定”。模型仍只使用现有 `setup` 工具，不新增独立模型工具。

- `setup.draft`：接收语义人物资料，调用现有建卡计算器产生完整候选卡，保存到当前战役的 setup 状态。返回实际预览数据、完整性结果和待解决项，不写正式 party。
- `setup.confirm`：提交当前已展示的合法草稿。草稿版本、完整性及提交幂等由宿主/内核检查；不重新掷骰、不重新调模型、不重新生成属性。
- `setup.complete`：检查确认提交及卡片完整性，记录一次交接。仅存在旧的 party 文件不再足够。

草稿版本、摘要、收据等由宿主铸造并注入，模型不抄写 opaque id。模型可以判断玩家是在确认或修改，但 `confirmed=true` 本身不能代替草稿存在、已展示、版本一致与完整性检查。

### 6.3 状态与恢复

逻辑顺序为：`setting_up → draft → reviewed → committed → ready_for_table → active`。
这些是现有 setup 状态中的阶段，不要求增加新的顶层存储体系。

- 草稿和展示后发生修改，旧版本的确认不可提交新版或覆盖新版。
- 普通确认应绑定当前已展示的草稿；显示失败时不能默认为玩家已看到。
- 明确的“修改并创建”或“直接创建”是独立的委托语义，不冒充对旧预览的确认。
- 重复确认、刷新、网络重试产生同一个正式角色，不复制角色或重新分配数值。
- 崩溃后恢复草稿、版本和未完成提交；保留逐字记录与所有失败证据。
- 取消只退出当前准备，不删除模组、战役或历史草稿证据。

## 7. 模组引导的存储与复用

扩展现有模块级 `character-guidance` 产物。需要表达的内容包括：

| 内容 | 作用 |
| --- | --- |
| 引导场景与人物 | 开场所在位置、接见者、已知公开前提 |
| 首段代入材料 | 环境/动作、第一句人物对白、简短旁白说明 |
| 模组建议 | 适合的职业、语言、训练、普通物品、卷入方式与硬约束 |
| 衔接边界 | 建卡可发生哪些介绍、正式游玩从何处继续、哪些事情还未发生 |
| 来源与复核证据 | 原页/图谱来源、player-safe 审查结果；只在宿主保存 |

- 文本生成继续使用带 `read/write/edit/bash` 的 Pi agent 和独立复核，不裸调补全。
- 系统提示、字段说明、给模型的指令使用英文；玩家段落由模型按 `play_language` 生成，不加 i18n 字符串表。
- 模组级缓存只保存可复用材料，不保存上一个玩家的名字、角色、关系或会面进度。
- 原 PDF 不重读作为默认建卡步骤；复用已准备好的图谱和来源证据，材料不足走现有补读路径。
- 模组来源/开场/语言/生成契约改变时创建新版本，不删除旧版；角色普通修改不重新生成模组引导。
- 切换版本后拒绝旧的背景简介/职业卡片格式冒充满足本规格；不能仅因缓存文件存在就跳过新契约检查。

## 8. 建卡场景到游玩的衔接

建卡时诺特已经接见并问过姓名，游玩不能再次“初次接见并问你是谁”。但沉浸场景也不能绕过内核写事实。

- setup 记录本次序幕实际完成的介绍、人物已明确说出的信息、最后一句对话及衔接位置。
- 模组缓存保存的是会面方案，当前战役 setup 保存的是本次会面进度，两者分开。
- 在正式确认提交时，内核将允许的序幕事实写入交接；游玩 opening 消费一次，恢复同一位置与对话进度。
- 如果当前世界状态只在建卡后创建，则在同一提交中初始化场景与已确认序幕事实；不能先写一段散文再假称它是世界真相。
- 对身份的介绍不等于接受委托；表达“为了房租而来”也不等于钥匙、预付款已取得。物品、金钱、线索或协议的变化必须分别有相应授权与收据。
- 建卡不提供自由探案、战斗、发线索的第二套运行时；玩家提前提出实质游玩行动时，保留意图并在正式建卡后交给 Keeper 处理。
- 交接失败可恢复，不重复序幕、不开两个并发 Keeper、不重写已确认角色。角色面板刷新不应因 setup 进程退出而成为永久错误；本次见到的首刷超时纳入此接缝验证。

## 9. 普通剧情的自由行动

用户明确否定截图中的“要先跟诺特谈哪一件”剧情按钮。

- 普通故事回合交代可观察场景、人物与后果后，等待玩家自然语言输入。可由 NPC 提问，不要求输出预制答案。
- 删除将所有疑问/决定强制转成 `ask.options` 的普遍要求；自由输入不能因不存在 options 而阻断。
- 前端不自动生成建议行动按钮，不把可自由表达的行动包装为固定选项。
- 真正闭合的机制决定仍可用专用结构化交互，如规则要求的防御方式；按现有规则决定何时需要，失败后不自动推销推骰/花幸运。
- 内核状态必须区分“等待普通玩家输入”和“有待结算机制选择”。不能仅隐藏 story 按钮而留下无法结算的 pending choice。
- 本次只改交互与投影边界，不改变骰子、战斗、追逐等规则算术。

## 10. 实施顺序与范围

1. 同步 `docs/kernel-rpc.md`：草稿、版本确认、完整性、序幕衔接、自由输入与机制选择的正式契约。
2. 扩展既有建卡计算与 setup 方法：复用旧版的完整语义输入和断言思想；完成真实 draft/confirm，不只改 prompt。
3. 接回现有 setup 会话和 Electron：自动展示实际角色草稿，支持自然语言修改/确认，保留现有会话记录。
4. 升级模组引导产物：场景、引导人物、对白、旁白提示与衔接边界；验证重复选择复用。
5. 调整 opening/ask/narrate 与 UI：普通剧情自由输入，可靠交接。
6. 用真实浏览器与规定的 Pi 驾驭器验证，逐项保留证据。

当前 `docs/kernel-rpc.md` §23.4 和 worktree 实现描述的是先前不完整方案；本 spec 是其替换提案，不能把两套要求同时交给实施者。修改正式契约时应重写旧小节而非持续追加矛盾补丁。

不包含：搬旧 web/Electron 框架、恢复旧 MCP/多代理机器、重做规则引擎、改解析供应商、扩展成自由编辑所有世界状态的系统、重构无关侧栏、提交/合并/发布或替换本机 App。既有未提交改动与旧战役证据全部保留。

## 11. 验收

### 11.1 确定性与接缝检查

- 草稿不进入正式 party；无草稿、未展示、非法或过期草稿不能作为普通确认提交。
- 当前展示的 card 与提交的 card 一致；重复确认不重掷、不重复创建。
- 改年龄只改变规则要求受影响的值，保留其他随机结果；修改后旧确认失效。
- 职业、兴趣、专业、语言、财务、背景与装备落到对应字段；所有待定选择清空或按所选规则合法解决。
- `setup.complete` 拒绝本次海伦样本这一类“点数未分完、装备仅在散文”的半成品。
- 模组缓存命中不再次启动作者/复核者；另一玩家不继承上一玩家的个人信息。
- 无需菜单也能关闭普通叙述回合并接收自由行动；机制选择仍可合法结算。
- 刷新、进程切换、重复提交、交接中断后状态可恢复，且不重复会面。

### 11.2 真实用户路径

玩法验证遵守 `docs/acceptance.md`：真实 Grok 与本主会话作为唯一玩家，一次一句，不预设批处理脚本、不用 fixture 冒充游玩。浏览器验证直接操作当前同一产品路径；RPC 驾驭器覆盖 setup/游玩接缝，两者不能互相冒充。

| 场景 | 输入与观察 | 通过条件 |
| --- | --- | --- |
| 冷启动选模组 | 全新会话选择 The Haunting | 出现诺特会面式引导与简短身份提示，不是背景梗概或行动菜单 |
| 最小描述 | 一句话给姓名、记者职业与谨慎性格 | 当回合不出草稿；先入戏追问一个（有承重缺口才两个），答完自动准备完整参数草稿；没有年龄/亲属/装备逐项采访 |
| 参数预览 | 不发确认 | 当前对话可看到真实属性、技能、财务、背景与装备；正式 party 仍为空 |
| 修改后确认 | 改年龄、删除一个亲属、指定编辑朋友，再确认 | 最新卡准确反映修改；点数/装备实际落账；确认前后未被无关重生成 |
| 明确代劳 | 另一新会话说“其余你定，直接创建” | 不追问、不反复确认；完整结果展示并合法提交，不能省略完整性校验 |
| 缓存复用 | 同模组另一新会话 | 使用相同有效引导，作者/复核者尝试数不增长，角色数据独立 |
| 自由行动 | 确认后直接向诺特提问或做自定行动 | 不出现那组剧情选项；已介绍身份不重演；Keeper 接受自然语言 |
| 冷恢复 | 在草稿或交接中断后恢复 | 恢复同一草稿/角色和会面进度，无重复卡或重复开场 |

至少再用一个开场人物/环境不同的已准备模组验证引导不是 The Haunting 特例。PDF 来源用现有视觉准备链路，模组准备验证与角色创建验证分别记录，不因一份 starter 成功就声称 PDF 路径完整通过。

保留：浏览器可见内容、逐字记录、draft/confirmation/commit 版本对应证据、角色文件、技能预算、装备数据、序幕交接记录、缓存命中/生成遥测。分别报告源码测试、浏览器完整建卡、RPC 游玩衔接与 packaged App 验收，未跑的闸门明确写未跑。

## 12. 评审结论边界

本规格确认产品行为与必要系统接缝，不宣称现有实现已满足它。进入实施前需把准确 RPC schema、所选建卡方法和序幕允许写入的事实类型写入正式内核契约；这些不得以“提示词以后会处理”跳过。
