## Problem Statement

At the original planning baseline, scenario maps could not reliably be viewed in the PipiCOC conversation: built-in registrations could lack image bytes, and image-handout rows only showed a name and availability stamp. The built-in card and region-state path now exists. The remaining product problem is making production PDF preparation and all knowledge/history cases reach that same player-visible result reliably.

Simply displaying an entire investigator map would expose unexplored layout. Simply masking that investigator map would also be incomplete: some published investigator versions omit secret spaces altogether. The product needs to show the part of the authored geography that the player has learned, including later discoveries, without exposing unrevealed geometry, labels, or Keeper annotations.

Success means the player can consult a useful map inside the active conversation, see it expand as knowledge is acquired, and resume with the correct map knowledge. Map records, rendered files, green tests, or a claim that a map was handed over are hollow completion if the player cannot actually see the right regions in the session.

## Solution

Use the current ModuleStore, ModuleGraph, tool-enabled visual reader, kernel transactions, host image renderer, and conversation projection as one path. Built-in maps and maps discovered while reading a PDF enter the same reviewed map representation. The representation connects source-backed map regions with the places they depict and separates safe geographical content from private annotations.

The Keeper judges what the investigators have actually learned through exploration, observation, or obtaining a document. The kernel records authorized knowledge changes with the existing transaction and receipt machinery. The host produces a player-safe image from that recorded knowledge. The player receives only the permitted image and public metadata, and can open it, zoom, pan, switch among already-known maps or levels, and reopen it without advancing the fiction.

Source preparation can be reused by different campaigns. Knowledge is scoped to the campaign and its existing worldline semantics. A source that is absent or cannot yet be safely segmented produces an honest unavailable/preparing result; it never falls back to displaying the full private image.

## User Stories

1. As a player, I want a built-in scenario's available map to appear in my conversation, so that I can understand the space without opening a source folder.
2. As a player, I want maps found in my imported PDF to use the same viewing experience, so that source format does not change how I play.
3. As a player, I want a map shown when spatial orientation is useful, so that I can follow movement and choose a route.
4. As a player, I want to request the current map in ordinary language, so that I do not need tool names or identifiers.
5. As a player, I want to reopen an already available map directly in the conversation, so that reviewing it does not require another model round trip.
6. As a player, I want viewing, zooming, panning, and changing visible map tabs to leave game state unchanged, so that using the interface does not spend fictional time or move my investigator.
7. As a player, I want only known portions of the map visible, so that unexplored rooms remain a discovery.
8. As a player, I want unknown rooms and levels absent from public names, thumbnails, tooltips, and image data, so that interface details do not reveal them.
9. As a player, I want entering a location to reveal only what was actually established as visible, so that crossing the threshold does not reveal the entire building.
10. As a player, I want knowledge gained by looking through a window or receiving a reliable description to be representable, so that knowledge is not limited to places I have entered.
11. As a player, I want receiving a floor plan to reveal only what that plan conveys, so that unvisited but documented areas can be known without revealing omitted secrets.
12. As a player, I want hearing a place's name to remain distinct from learning its layout, so that a rumor does not turn into a detailed map.
13. As a player, I want a secret space to remain concealed until its discovery is established, so that a map does not spoil the investigation.
14. As a player, I want a newly discovered space to appear even if the published investigator map omitted it, so that the map remains useful after a discovery.
15. As a player, I want Keeper notes and undiscovered annotations removed from otherwise visible geography, so that seeing a room does not reveal everything the book says about it.
16. As a player, I want known layout to remain available after leaving an area, so that exploration creates a durable spatial reference.
17. As a player, I want map access to grant no new clue, movement permission, or physical document by itself, so that viewing the interface is not a hidden game action.
18. As a player, I want floor and map selection to show only what I already know, so that navigation controls preserve the same secrecy as the image.
19. As a player, I want interface words and added public labels in the play language, so that an English source can support my chosen language of play.
20. As a player, I want authored text on a physical map handout preserved, so that presentation does not silently rewrite evidence or intentional mistakes.
21. As a player, I want my map knowledge restored when I resume the campaign, so that restarting the application does not erase exploration.
22. As a player, I want a new campaign using the same book to start with its own knowledge, so that another campaign's discoveries do not appear in mine.
23. As a player, I want worldline switches and historical map cards to use the correct knowledge state, so that future discoveries do not leak into earlier views.
24. As a player, I want a missing image or failed preparation explained honestly, so that a success stamp does not promise a map that cannot be opened.
25. As a Keeper, I want map names, available regions, and the supported display action projected together, so that finding and showing a map does not require assembling several unrelated lookups.
26. As a Keeper, I want to identify maps and regions by semantic names, so that the host owns opaque identities, revisions, receipts, and file paths.
27. As a Keeper, I want map preparation to preserve source relationships and distinguish private and public versions, so that the displayed geography is grounded in the scenario.
28. As a Keeper, I want a later need for a map to use the existing demand-reading path, so that opening a long scenario does not require preparing every map first.
29. As a Keeper, I want uncertain region geometry or disputed source correspondence held for review, so that extraction uncertainty cannot silently become player-visible content.
30. As a maintainer, I want built-in assets and PDF-derived assets to share the same consumer contract, so that subsequent maps do not require scenario-specific rendering code.
31. As a maintainer, I want invalid, stale, or replayed knowledge changes handled by the existing kernel rules, so that map updates remain atomic and idempotent.
32. As a maintainer, I want corrected source assets to retain explicit identity and revision binding, so that old reveal coordinates cannot expose unrelated pixels after a source update.
33. As a maintainer, I want the player-facing asset channel to serve only authorized derivatives, so that hiding content is enforced before it reaches the renderer.
34. As a maintainer, I want legacy saves, source files, and playtest evidence preserved, so that adding maps does not rewrite or destroy previous play.
35. As a maintainer, I want real built-in and fresh-PDF sessions plus actual UI evidence to validate the feature, so that fixtures and successful image generation cannot substitute for player-visible behavior.

## Implementation Decisions

1. **One existing product path.** Keep the seven Keeper verbs, one production TypeScript kernel, one ModuleStore and one ModuleGraph. Extend existing asset/handout metadata, `apply` knowledge effects, read projections and structured conversation delivery. Do not introduce another map truth store, agent runtime, public tool family, or optional Mod that can disable secrecy. Preserve ordinary handout behavior.
2. **Contract before implementation.** The first vertical slice records the map representation, knowledge mutation, read projection, receipt, asset delivery and failure semantics in the canonical kernel RPC contract before code changes. It also establishes the shared shape required by later tickets. The specification owns intent and acceptance; the canonical contract owns exact fields and enums. Later tickets must not invent alternative shapes independently.
3. **Source representation.** A map is authored visual material with stable semantic regions, their source-bound geometry, depicted places, public presentation metadata, and any alternative source regions needed for later discovery. Regions may be parts of rooms, rooms, floors or outdoor areas; graph scenes are not automatically reveal units. Reuse existing asset/handout nodes and typed relations. Add only metadata needed for this representation, not a second navigation graph.
4. **Common preparation.** Built-in maps with valid bytes use this contract directly. Missing built-in bytes can be prepared from a matching local source through the existing host source facilities; the first sample uses the supplied Rulebook. Never hard-code a developer's absolute source path. PDF discovery, segmentation, place correspondence and annotation classification are performed by the existing tool-enabled Pi reader and independent source review. Regular expressions or fixed scenario tables cannot make these semantic decisions. The host validates references, coordinates, identity and publication; the kernel never parses PDF or image contents.
5. **Map variants require explicit correspondence.** An investigator version may omit secret spaces or use a different origin, scale or arrangement. Do not transfer masks by assuming two images align. Identify region correspondence from the original source and review it. Later-discovered geometry can use a separately reviewed safe source crop or layer; creating new geography or generatively redrawing the author's plan is outside this feature.
6. **Knowledge has a writer.** The Keeper judges whether an observation, exploration result, document or other established information supports revealing a region. Its proposed reveal uses the existing `apply` transaction path and action-admission rules, identifying the map, semantic regions and the in-fiction basis. The kernel validates references and supported effects, records the resulting knowledge and receipt, and changes nothing on rejected batches. Pure viewer operations never masquerade as a map-acquisition or exploration effect.
7. **Knowledge is distinct from visits and document possession.** Do not reveal an entire scene from `visited_scenes`, an entire map from `player-safe`, or everything from `handouts_shown`. A discovered room does not authorize hidden compartments or annotations inside it. A received plan authorizes the information actually conveyed by that plan; an unreliable or incomplete document remains a document rather than becoming ground truth. Existing knowledge is retained without implying current line of sight or current NPC positions.
8. **Knowledge has a reader and an action.** The Keeper's existing local projection exposes the available map and region names together with the supported reveal/display action. The player-facing table projection exposes only authorized views and public metadata. The Keeper can place the map in the conversation when needed; the player can reopen it directly. Existing offer telemetry may record whether the map was used, but cannot feed an obligation or display quota into subsequent turns. Each added field has an identified producer, reader and actual consumer.
9. **Secrecy is enforced in the host.** Produce an opaque, flattened player derivative from permitted geometry and safe content. Do not pass the private PDF, full base map, hidden region coordinates, private labels or private image URLs through map cards, public projections, thumbnails, accessibility text or the map delivery channel. Unknown areas must reveal neither faint underlying pixels nor outlines deliberately outlining undiscovered spaces. The viewer receives only the authorized derivative and public metadata. This governs player-facing product surfaces, not the machine owner's independent filesystem access.
10. **Reuse the existing image transport.** Use the established host-controlled asset channel with an appropriately narrow derivative scope and verified campaign/view ownership. Do not encode the full source image into ordinary transcript text or grant a broad private-source directory merely to make a map load. Runtime identities and cache keys are host-owned; the model addresses semantic map and region names.
11. **Conversation behavior.** A map can appear as a structured card associated with the Keeper's delivery and can be reopened from the current session. Provide zoom, pan, and selection among known maps and known levels using the same map module. Multiple maps cannot overwrite one another or collapse merely because names match. Showing a map conveys spatial reference and never asserts that the investigators acquired a physical document. Viewing a public card is a read-only host action and does not require a synthetic Keeper turn.
12. **Persistence and temporal views.** Store map knowledge with canonical campaign world state and existing transaction/history machinery. Basic persistence, rollback, replay safety and fresh-campaign isolation apply from the first slice. Bind each delivered derivative to the map/source revision and the knowledge snapshot that authorized it. Historical cards retain their delivery-time view; a current-map action uses the active campaign and worldline. An old chat card must not silently change into a later, more revealing map. Worldline forks, switches and confluence follow the existing worldline knowledge policy, including explicitly supported retained knowledge, without adding a new policy.
13. **Source updates and old saves.** Reuse accepted map preparation across campaigns without sharing their revealed sets. Source updates cannot reinterpret previous masks against different geometry. Preserve revision bindings; incompatible revisions require re-review before a new derivative is delivered. Existing saves without map knowledge begin conservatively and may recover only from compatible canonical disclosure evidence. Visits or unqualified whole-handout markers alone cannot authorize a room-by-room backfill. Preserve all source and play evidence.
14. **Demand and failure behavior.** Prepare map material only when relevant to opening play or a later source need; do not scan or segment every map before a long book opens. Use the existing source queue, deduplication, foreground priority, cancellation and review gates. A visual-reference failure leaves the last authorized view available when valid and explicitly reports the missing update. It must neither invent map pixels nor undo a separately completed game action. If the underlying game action itself lacks required source facts, retain the existing pre-effect material gate.
15. **Language.** Generate public titles and added labels in `play_language`, or project the single English system source through the existing presenter. Preserve original physical-handout text and source bytes, including deliberate inaccuracies. No language-specific dictionaries, branches or forced rewriting of raster source labels are introduced.
16. **Planning and implementation ownership.** The parent is a specification umbrella. Six child tickets carry the executable slices; blocker completion and unique ownership determine which can start. This reconciliation updates planning and tracking; subsequent implementation and live acceptance belong to the owners the user assigns.
17. **Useful disclosure units are an acceptance requirement.** A source map that contains separately knowable areas must support independent disclosure of those areas. Do not publish an entire settlement or floor as the only usable unit merely because its full-page crop is easy to verify. Whole-map disclosure is legitimate only when the fiction establishes knowledge of all information it exposes. An uncertain subregion remains unavailable/preparing; it must not widen the reveal. The reader and reviewer determine geography semantically from original images, with the existing deterministic geometry and source checks.
18. **Focused preparation and repair keep the same boundary.** The requested use, focus and question define the task; pages opened for navigation or context do not define a whole-chapter extraction obligation. Map labels do not demand full NPC dossiers or later encounters. Necessary facts affecting the present interaction, access or safety remain in scope. Preserve successful source/review evidence where still valid; do not repeatedly run inherited oversized drafts as evidence of fresh preparation efficiency.
19. **Source compatibility needs an observable check.** A source or geometry update must not broaden a previously authorized region solely because its semantic id is unchanged. Verify compatible corrections, incompatible layout changes, old-card snapshots and current-map reads through existing publication/state interfaces. Record any needed exact compatibility rule in the canonical contract before changing it; do not introduce another map state store or let a new view hash stand in for authorization.

## Testing Decisions

The primary acceptance seam is the existing setup/play-to-conversation path: choose a built-in module or original PDF, play naturally with the real Keeper, and inspect the resulting receipts, durable knowledge, permitted image bytes and actual player-visible map. This is the same success criterion approved in the preceding conversation. Supporting tests exercise public interfaces rather than internal helper layouts.

1. **Initial complete slice.** A real built-in map is discoverable by the Keeper, one established region becomes visible in a conversation card, everything else remains unavailable, and reopening the card changes no clock, location, RNG, receipts or knowledge. Asset registration without an image in the UI fails this check.
2. **Knowledge semantics.** Cover visiting only part of a floor, observing without entering, acquiring a limited plan, hearing only a location name, discovering a secret region, and leaving a known area. At least one example requires different public and private source layouts. The real Keeper must choose disclosures from the interaction, not a scripted keyword router.
3. **Public data and pixels.** At the existing host projection and asset interface, assert that unrevealed geometry, labels and source URLs are absent. Inspect emitted pixels for opaque concealment and source annotation exclusion. Exercise guessed derivative identifiers, another campaign's view, bad references and stale revisions. A renderer-only overlay test is insufficient.
4. **PDF publication.** Exercise the existing reader-to-publication seam with real original pages, explicit source identity, normalized crop geometry, independent review and later demand reading. Invalid references, uncertain mapping and rejected review must not publish a usable player image. Test a map first needed after the opening, without a whole-book preparation requirement.
5. **State and history.** Through current TypeScript RPC and campaign history interfaces, check atomic failed batches, idempotent retries, restart, separate campaigns, worldline transitions, historical card snapshots, stale source revisions and old saves without map state. Reuse the current transaction, handout, source-publication and worldline test patterns; do not mutate the frozen historical Python oracle for new behavior.
6. **UI behavior.** Verify actual image display, zoom/pan, known-only map and floor selection, reopening without a model turn, play-language presentation, unavailable states, and correct card identity in the conversation. Reuse the current image asset-channel and mechanics-renderer test seams. Run the existing Electron suite against its recorded baseline; do not add baseline entries to conceal regressions.
7. **Real tables.** Follow the repository's canonical RPC driver with Grok as Keeper and the main session as the sole player, one natural utterance at a time, from setup/opening to a natural ending or genuine blocker. Preserve all evidence. Use a built-in The Haunting run and a separate fresh original-PDF run; the latter must exercise production map preparation rather than manually inserting map records. Bounded map checks are labeled bounded and cannot stand in for full table evidence. Actual PipiCOC UI observation is an additional display gate, not an alternative fake or scripted play method.
8. **Proportionate checks and performance.** Run relevant kernel, extension and UI regression checks and the required integrated suites. Never run two pytest suites concurrently. Record map preparation and reveal/display latency, distinguish cold preparation from cached reuse, and confirm reopening a prepared view needs no model call. No speed or arbitrary-map extraction-quality claim is made by writing this plan.

## Out of Scope

- A tactical VTT, combat grid, token manipulation, line-of-sight simulation, lighting engine, pathfinding or map-based movement controls.
- Generating maps for modules with no source map, redrawing authored geography, or adding new rooms, clues, mechanics or scenario content.
- A separate map database, Keeper agent, source scheduler, OCR pipeline, Python production kernel, or replacement for the seven verbs.
- Revealing all locations because a map is labeled player-safe, all rooms because a scene was visited, or all secrets because a document was acquired.
- Per-player multiplayer permissions or new party-splitting knowledge rules beyond the current campaign/player model.
- New worldline memory rules, rewriting old narration/receipts, deleting evidence, or silently migrating every existing campaign.
- Rewriting authored raster-map text into translated pixels, adding manual region-authoring tools for players, or making the player draw reveal masks.
- Republishing the supplied Rulebook or bundling its private source bytes as part of this planning task. Local preparation uses a source available to the user; any distribution must respect the actual asset's existing availability terms.
- Unrelated UI redesign, onboarding changes, rules work, optional gameplay Mod changes, dependency upgrades or deployment.
