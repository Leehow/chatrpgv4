> 状态：待执行的测试委托，不是测试报告。本轮只修订计划，未启动服务/App、未开桌、未导入 PDF。
> 计划日期：2026-09-15。初版只读核对时源码为 `0.9.3a / 1318b1674`；初版计划提交 `e9eac49dc`。源码 HEAD 不证明已安装 App 或已运行服务来自同一提交。
> 本次用户更正：允许内置浏览器；发现 bug 要形成修复与复测闭环，非阻塞并行修，阻塞修好再继续。文件路径沿用初版，便于已有委托继续引用。

## 1. 目标与成功定义

用户要知道：**PipiCOC 能否让真实玩家顺畅跑完剧本；玩家认真地偏离后，Grok KP 能否在保留选择、因果和既有状态的前提下，提供可信的回归路径并真正接回剧本。**

成功不是回合数够多，也不是 KP 宣布“故事结束”。必须有实际调查、选择、后果和可证明的收束。短本和鬼屋跑到结局；长本从开场开始，至少跑完一个完整调查章节。

**测试同时负责修复闭环，不是只交 bug 清单。** 发现问题后保留复现证据、安排修复、核对修复实际生效并在原 UI 路径复测。非阻塞问题可以边测边派 worker 修；阻塞问题不跨过去。worker 尚未交付、验证未通过或 GUI 尚未复测，都不等于修好。

偏航测试有两个独立结果：

1. **回归能力**：是否出现合理的连接机会，玩家因这个机会行动后，是否真正回到主线。
2. **自主性与连续性**：是否允许偏航，支线是否有内容与后果，回归时是否保留这些后果。

强制传送回主线、替玩家决定、修改已确立事实、用所有 NPC 重复催促，均不算“圆回来”。有逻辑的永久离开可以是合理故事结局，但不能记为“回归主线成功”。

## 2. 固定条件与方法边界

### 2.1 执行环境

- 被测对象：**PipiCOC 的真实产品 UI 与真实后端**。优先在内置浏览器访问已核实的产品 Web 入口；原生补测使用唯一安装包 `/Applications/PipiCOC.app`，bundle id `com.leehow.pipicoc`。
- 交互方法：**内置 browser 工具优先**，通过页面选择模型、导入 PDF、建卡、开桌、输入玩家行动和选择结构化选项。共享 renderer 的布局、状态与玩法无需为了“更真实”重复搬到桌面。
- 等价边界：相同页面不自动证明后端也相同。执行前核对接的是真实 PipiCOC setup/play、TS 内核、模型及实际战役存储，不能拿通用聊天页、mock、静态预览或空壳页面当实测。Web 不能覆盖的 preload/主进程、原生菜单、OS 文件对话框与安装包行为，才用 computer use 补测；报告分开标明覆盖面。
- KP：**Grok 4.6，thinking/effort = low**。若模型目录显示 provider，记录完整 provider/model id，预期模型为 `grok-build/grok-4.6`；不是 Grok 4 fast、其他 Grok 版本或执行 AI 自己。
- 玩家：负责该任务的外部 AI 主会话；只扮演一名认真玩的玩家。一次提交一个自然、连贯的行动或问句，等本轮完成再决定下一步。
- 默认玩家语言：简体中文。英文长本也用中文游玩，用于观察英文来源到中文游玩的连贯性；不人为要求逐句翻译。
- 每个任务新建独立战役，角色背景与能力尽量可比；不要求篡改骰子或复制存档来制造完全相同结果。
- 各任务从同一基线开始；边测边修允许版本演进，但记录每个修复提交/构建、应用时点、受影响回合和复测编号。不把不同版本拼成“同一版本全通过”。保留原战役和原失败证据，修复后优先沿原局继续。

用户已明确允许内置浏览器，故本计划采用真实 Web/App GUI，而不是仓库默认的 `tests/play/driver.py` 玩家传输方式，也不改写默认验收契约。不授权假守秘人、批量脚本或合成回合。启动真实 Web 服务、必要编译、代码修复和回归测试可以使用开发工具；**玩家行动与最终体验验收仍走 UI**。

### 2.2 允许与禁止

**允许：**内置浏览器的页面观察、语义操作、截图、控制台/网络证据；必要原生步骤的 computer use；只读核对实际日志/战役状态；独立审计 AI 对照原始剧本。日志读取仅辅助举证，不代替 GUI 体验。授权范围内发现的产品 bug，由修复 worker 修改系统路径、补回归、运行必要构建/测试，主会话负责实际 UI 复测。

**禁止：**

- 用 RPC、CLI、开发者控制台、直接 provider 调用或脚本绕过被测 GUI 来开桌/行动/结算/切模型。真实接线的 Web 开发服务可以测，mock/静态预览不可以；修复阶段的自动化回归不能冒充玩家实测。
- 手改战役状态、会话 JSONL、模型切换记录或模组图伪造成功；尤其不能伪造 `model_change` 或 effort。源码的真实缺陷允许按 §8 修复，不能通过弱化守卫、刷绿测试、手补本局剧情或改变已获知的结果来掩盖它。
- 执行 AI 自己写 KP 回答、代掷骰、补造线索，或安排第二套 Keeper 接管故事。
- 预先生成一串玩家台词、批量发送、关键词路由、固定场景模板刷回合。下面的玩法策略不是脚本。
- 玩到一半读隐藏模组图或 PDF 解答，再把答案用于玩家行动；把审计结论、计划或“请把我拉回主线”发给 KP。
- 为重新开始而删除旧战役、逐字记录、遥测、模组数据或测试证据。
- 擅自打包、安装第二份 App、发布/推送或重启 PipiUI 宿主。允许把本次修复在安全节点应用到被测 Web 服务；不得让自动重载打断正在结算的回合。需要重包/原生重启等额外授权时明确提出，不拿 Web 已修复宣称旧安装包也已修复。

若执行 AI 没有可用 browser 工具，产品可由已授权的 computer-use App 路径继续测试，但须记录方法变化；两种 UI 能力都没有时报告缺失。若只是 Web 没接真实后端，不能将其记成通过或拿 mock 顶替；按入口问题定位，或在记录边界后使用真实 App。

源码接线已确认：`browser.tsx → RemoteBrowserApp → App` 是同一套 React UI；正常模式 `createWsHost → /ws → PiHostBackend`，server 配置使用 `pipicoc/rpc`、`defaultPack: coc-keeper`、`product.id: pipicoc`。这证明存在真实接线路径，不等于本轮已运行成功或所有功能与 App 完全等价。

从仓库根 `/Users/haoli/leehow/code/chatrpgv4-wt-pi-coc-v2`，后续执行者可用：

```bash
npm --prefix Electron run dev:browser
```

- 此命令已包含 `build:web`，不必预先重复构建 Web。项目依赖与 TS runtime 产物仍须按源码运行说明准备；需要时先在仓库根运行 `npm run build:runtime`。不要恢复 Python 后端或把过期产物当最新修复。
- 命令监听 loopback `127.0.0.1:5173`，公开给本机浏览器的规范 origin 是 `http://localhost:5173`。若端口冲突，不杀未知进程；为自己启动的服务选择配置一致的空闲端口并记录。
- **使用服务实际打印的 pairing 链接进入**，不要从裸 `/` 的未配对状态判断产品故障；配对后保持 `localhost`，不要切成 `127.0.0.1` 导致 host-only cookie 不匹配。记录脱敏后的 origin/路径，不把配对 secret 放进报告、截图或 worker 简报，也不关闭配对保护图省事。
- 同一配对链接重复领取会替换先前连接。不要让修复/审计 worker 或另一玩家窗口抢领它；重新连接要核对是否恢复到原战役。
- `VITE_PIPIUI_DEMO=true` 构建使用 mock；真实测试不能启用。`electron-vite dev --rendererOnly` 缺少宿主传输，不是可替代入口；`pipicoc/dev` 启动 Electron，也不是 Web 命令。
- 当前 server 配置默认接仓库 `.pi/coc-agent`，不是独立 App 的 userData；以实际运行配置核对。旧 server README 中的 `~/.pi/agent` 描述不能覆盖当前接线，不为测试复制凭据到全局 home。
- PDF 新建入口是 HTML file input/拖放，不依赖 Electron 专有选文件接口。仍需实测浏览器工具的本地文件选择及实际上传链路，不能凭代码存在断言导入成功。
- server 对自身内置的 Finder、computerUse 等能力可能降级；它们不是外部测试 AI 的 browser 工具。关闭这些产品能力不代表不能用内置浏览器观察测试，也不证明原生能力已经验收。

## 5. 派工与信息隔离

- 推荐每个任务交给一个新 AI 主会话，传本计划 + 一个任务 ID；模型与成本由执行方安排，KP 始终是产品内 Grok 4.6 low。这个主会话同时负责玩家决策、观察与修复调度，不把桌面/browser 验收交给看不到界面的代码 worker。
- 同一浏览器目标、会话/战役或桌面 **一次只能有一个 UI 执行者**。修复 worker 可并行读代码、隔离改代码和跑测试，但不抢 UI、不启动第二个 KP、不向在玩的战役写入行动。
- 可分给三名 AI 各负责一个剧本的三个任务，但每局用新玩家上下文；已读过前一局结局的玩家必须标注“非盲测”，不能声称未知剧情。
- 多局并行只有在浏览器目标、后端会话、数据目录及设置均已证明隔离时才可用；默认串行玩局、并行修 bug。不要为了本计划自行创建另一份本机 App。
- 推荐执行顺序：H-MAIN → A-MAIN → M-MAIN，先验证三条开桌路径；再依次执行 H/A/M 的 DETOUR、SIDE。当前局阻塞必须先修复复测，不能开下一局来掩盖它。真正独立的既有测试可以继续，但总负责人仍须持续跟进原阻塞，不得把它变成无人处理的清单。
- **玩家与审计分离**：玩家游玩期间只使用 UI 给出的公开信息。独立审计 AI 在每局结束或真实阻断后，使用只读副本对照原始 PDF/内置来源和日志，不把隐藏事实反馈给仍在游玩的玩家。
- 审计 AI 不使用正在被执行者控制的桌面、不修改数据、不接管 KP；读 PDF 时保留页码/来源位置。剧情判断是语义审计，不能用关键词计数替代。

## 6. 每局通用流程

### A. 开局与证据锚定

1. 先核对真实 Web 启动路径和接线。需长驻服务时在可观察终端启动，浏览器打开该服务实际 URL，观察页面并确认真实 PipiCOC 后端与存储；不能用外观判断。原生步骤才激活 `com.leehow.pipicoc`，并确认唯一路径 `/Applications/PipiCOC.app`。
2. 记录本局 `task_id`、唯一 `run_id`、开始时间/时区、Web URL/启动命令、实际服务版本/可得构建身份、数据 home 和屏幕环境；原生补测另记 App 构建。无法取得构建 SHA 就写“未知”，不要拿源码 HEAD 代替。
3. 在实际 UI 提供模型控件后选 **Grok 4.6 / low**；截图保留结果，不捕获凭据。若控件在新建后才出现，就在新建后选择，不臆造页面入口。
4. 若 low 不在列表，或选后无效，先用新观察、语义元素或键盘重新确认。两次可靠尝试仍不能成功，记录配置阻塞，按 §8 定位修复，不偷偷换模型/effort，也不伪造记录。
5. 经新建流程选中文、内置鬼屋或指定原 PDF，正常完成建卡。记录导入开始/结束、可见进度、失败提示与重试情况。正常支持的继续/重试可以使用，但须保留首次失败证据。
6. **进入实际游玩会话后再次核对 Grok 4.6 / low。** 建卡/setup 和 play 可能不是同一个会话，不能拿建卡窗口截图证明 KP 的设置。没有满足条件前不发首句玩家行动。
7. 记录战役名称/id、模组关联、会话标识。GUI 不显示 id 时可只读从日志定位；不得写回。

browser 操作优先用语义 locator，导航/提交后重新观察；等待较长生成用 watch，不用高频轮询和反复发送。原生 computer-use 才走新观察 → 无障碍元素/键盘 → 必要时像素。元素失效先重新观察，同一做法失败两次就换方式，不盲点；不得改用接口跳过产品缺陷。

### B. 正常玩一回合

1. 阅读 KP 本轮完整输出和结构化规则选项。
2. 以角色当前知道的事，决定一个行动/问句；输入并发送一次。
3. 等待本轮结束；忙碌时观察状态，不重复点击发送，不提前排队下一回合。
4. 观察叙事、骰子/机制卡、人物卡/资源、线索和场景变化是否一致，再做下一步。
5. 关键节点截图：开场、重要线索、首次实际检定、状态变化、偏航开始、支线后果、回归机会、实际回归、结局/章节收束、任何故障。
6. 发现故障立即按 §8 留证和分流；继续之前确认当前行动不依赖未修好的问题。worker 有结果或到安全节点时检查修复状态，不埋头跑完几十轮才看。

不规定“必须 N 回合”。真实决策和因果链才是覆盖。正常等待不是产品失败；异常延迟要记录时间，不用快速刷输入掩盖。

### C. 跨回合顺带观察（不为凑覆盖硬造情节）

| 能力 | 可观察证据 |
|---|---|
| 玩家行动准入 | KP 不替玩家实施未选择的关键行动；建议、猜测与已经行动区分清楚 |
| 数值与状态 | 需要结算时有机制卡/收据；人物卡的 HP、SAN、物品等与实际后果一致；无凭空恢复或重复扣减 |
| 信息与保密 | 新线索有取得过程；猜测不直接升级为模组事实；不提前泄露隐藏答案 |
| NPC 与连续性 | 称呼、动机、关系、承诺及已知信息跨回合保持一致 |
| UI 与阅读 | 正文中文可读；数值/规则选择有专用结构化呈现，不靠正文复述替代；无重复正文、消失的选项或无法输入 |
| PDF 路径 | 导入可理解；需要新区域资料时能继续；没有把缺资料静默编造成权威剧本事实 |

没有自然发生的战斗、疯狂、推骰等记“未覆盖”，不强迫发生，也不据此扩张本计划。读页/补读是否真的发生由实际日志辅助证明，不能单凭流畅文风断言。

## 7. 三种玩法的执行策略

### MAIN：主线完成能力

- 接受合理的初始动机，正常询问、搜集线索、访问有关人物/地点，根据公开信息推进。
- 遇到失败检定或暂时死路，像认真玩家一样尝试替代调查，而不是请求剧透、自动成功或跳到结局。
- 可以提出角色合理问题，不故意拉出无关目标，也不牺牲基本谨慎来赶进度。
- 终点应包含调查结果、关键冲突/选择的后果及可辨认的故事/章节收束。
- 合乎规则的失败结局可以算“到达结局”，但须区分游戏失败与产品失败。若开场就死亡/退场，不能拿这条捷径宣称主线能力充分覆盖；保留原局，标覆盖不足，需要补测则新建局。

### DETOUR：有意离开主线

1. 先进行足够的正常开场，让玩家知道当前调查目标以及至少一条可行线索；在测试笔记中记录，不发给 KP。
2. 从眼前真实情境选择一个有角色动机、但不沿当前线索推进的目标。例如处理生计、寻找另一份委托、调查不相关的疑点或准备离开当前调查地点。**选择随现场生成，不照抄示例，不凭空宣称不存在的地点/NPC。**
3. 真正投入行动，让偏离有时间、地点、资源或关系上的后果。只说一句“不去了”然后马上回头，不算已测试偏航。
4. 不主动提醒 KP“这局在测试回归”，不自己凭攻略设计回归桥梁。允许拒绝一次牵强的催促，但不无条件拒绝所有新信息。
5. 一旦出现角色会在意的合理新机会，按角色动机作选择；若愿意接触，就沿它继续，观察是否回到原案的实质调查。
6. 返回后继续到本任务终点；仅 NPC 再提剧本名、任务提示复读或玩家口头答应，不算实际回归。

### SIDE：认真做支线，再自然跑偏

1. 从真实游玩中出现的次要人物、承诺、物品、地点或疑问中选一项值得认真追究的目标；不要先读 PDF 挑“官方支线”。
2. 真正帮助、追查或履行承诺，观察其是否有具体信息、人物动机、选择与后果，而非一问即空。
3. 顺着这个目标的新因果再走一步，让它成为与原调查不同的行动方向。测试笔记明确标出“支线开始”和“支线导致偏离”的分界。
4. 看 KP 是否把支线形成的人脉、代价、信息或时间后果合理连接回原案，而不是取消支线、瞬移人物或忽略之前做过的事。
5. 对可信回归机会按角色逻辑回应；回归后主动使用这条支线已经获得的东西或承担其后果，检查连续性，再继续到终点。

若 KP 从不允许形成真实支线，或所有问题都被敷衍后赶回原案，记录支线能力失败；不要由玩家自己编一个支线冒充产品交付。

### 对“圆回去”的五项核验

| 维度 | 通过表现 | 失败信号 |
|---|---|---|
| 允许偏离 | 玩家选的行动真正进入故事并产生后果 | 否认选择、替玩家行动、强制传送 |
| 支线质量（SIDE） | 有具体对象、目标、信息/代价和可延续后果 | 空泛寒暄、循环回复、一次性填充 |
| 因果连接 | 回归机会来自既有人物/线索/世界变化，或合理的新因果 | 所有人突然掌握同一秘密、无来源送答案、反复“必须回去” |
| 状态保留 | 时间、资源、物品、关系、承诺延续 | 为接回主线抹掉行动、改写既定事实 |
| 实际回归 | 玩家自愿行动后重新推进原案的有效节点 | 只说“回归主线”，没有新的调查进展 |

每项写“通过/失败/未证实”及一个具体回合锚点，禁止只给模糊总分。新增支线本身不等于违背剧本；审计关注是否破坏核心真相、既定事实或公平性，不要求照搬场景顺序。

## 8. 边测边修、阻塞与恢复

### 8.1 发现即分流，不留无人处理的问题

**每个确认的产品 bug 都要有负责人、修复结果和 UI 复测结果；“派了 worker”不是结果。** 建立轻量 bug 台账，编号与任务/战役/回合关联。误报可以基于证据关闭；真实缺陷不能自动降级成“留后优化”。与本轮测试无关的功能扩展另报，不混入修复。

| 类型 | 立即动作 | 能否继续玩 |
|---|---|---|
| 非阻塞 | 留证后立即派独立修复 worker，记录影响范围与可继续的路径 | 仅继续不受影响的当前局步骤；下一步依赖该问题时转阻塞 |
| 阻塞 | 留证并暂停相关局/步骤，立即定位与修复 | 修复实际加载、原路径复测通过后才能继续；不能跳章、开新局或换模型逃过 |
| 真实外部阻碍 | 查明缺的是凭据、服务、权限或工具能力，保留证据并提出具体最小解阻请求 | 相关步骤暂停；不能假造完成。原问题继续有人负责 |

是否阻塞由**结果还能否信任**决定，不只看输入框能否继续打字。状态损坏、遗漏/重复结算、错误 KP/effort、授权越界、秘密泄露导致后续玩家决策污染、关键资料缺失或不可恢复循环，都可能使后续证据无效，应暂停受影响范围。未知影响先保守按阻塞定位；只有证据证明独立才能边玩边修。

### 8.2 给修复 worker 的最小完整简报

- bug ID、预期行为、**玩家原话与 KP 实际输出**、精确 URL/界面控件、按顺序的复现步骤和回合/时间戳。
- 原始报错、console/网络失败、服务端日志摘录和截图路径；不要只写“按钮没反应”“KP 不对”。密钥、配对链接 secret 和其他敏感信息脱敏，URL 仍保留足以复现的非敏感路径。
- 已定位的当前系统路径/文件/函数、可写 scope、不允许改变的行为、验收标准和明确的回归命令。未知位置先只读定位，再确定修复切片，不要求 worker 自行重新定义目标。实际调用的 verify 命令要写进委派字段，回归仅跑相关范围；记录其真实退出码。
- 阻塞程度、正在玩的战役与当前测试版本、安全集成点、禁止操作真实战役或 UI 的边界。
- 当前生产内核只有 `kernel-ts/`；宿主 `runtime/`、扩展 `extensions/`、PipiCOC 接线 `pipicoc/` 与 `Electron/`。不查旧 Python 找补丁、不恢复退役生产代码。涉及 RPC/状态形状先遵守契约；修系统路径，不手补这一本/这一回合的内容。

同一问题用同一个 worker 连续实现、测试、修正与重验；实现与相关回归用例同属它。独立 bug 可并行，相同函数/状态接口的改动由一个 owner 处理。worker 使用隔离工作树，不能在主会话正在运行/修改的同一区域抢写；不得并发启动两个 pytest。需要更换处理方式时保留已做工作与证据，不盲目重复失败尝试。

### 8.3 修复必须经过主会话的真实复测

按以下状态流转，台账不得跳级：

`发现 → 已留证/已分级 → 已派工 → 修复中 → 代码与回归通过 → 已集成/已加载 → UI 原路径复测通过 → 关闭`

1. 非阻塞修复期间，主会话继续真实游玩并跟进 worker 信号；阻塞期间，主会话留在阻塞现场处理修复与观察，不靠推进其他剧情回避它。worker 卡住、失败或没有结果时检查状态/日志，继续原 worker 或调整已证伪的做法，不能派完就忘。
2. 收到修复后读变更，确认确实修了系统缺陷；检查实际回归命令退出码。代码测试通过只说明代码层通过，不说明 UI 正确。失败则退回修复，不能合入正在测的版本继续赌。
3. **控制集成时点。** 非阻塞 worker 在隔离树修，测试运行版本保持可识别；在本轮已结算/输入空闲的安全点才切入修复。若 runtime 自动合并会触发开发服务 HMR、清空界面或重启后端，则用固定的被测构建/副本隔离，或暂停游玩后再允许变更进入；不能名义“并行”却让热更新打断结算。
4. 记录修复提交/构建及生效时点，核对服务编译/启动日志和页面确实加载新版本。需要重启本次自建 Web 服务时先保留战役与进程状态，仅操作该服务；**不得重启 PipiUI 宿主**。原生安装包需要额外发布动作时另处理，不混称已更新。
5. **主会话走原 URL、原控件和原操作序列复测**，将修复前后证据配对，同时检查相邻状态不回归。UI 问题用 browser 观察/截图/console 验收；若修复涉及响应式布局，另检查 desktop/mobile 两视口，不因此重复整套九局。
6. 阻塞解除后才继续原局的下一步；非阻塞也必须补上真实复测再关闭。再失败就回到同一个 worker，不能拿“已经提交”顶替通过。
7. 原操作若不可逆，不对已结算回合再次发送相同行动。保留原失败现场；用产品正常支持的恢复继续原局，或新建明确标为复测的独立局重现前置条件。不能手改存档、倒带事件或重掷以伪造同一路径。原局因此不可恢复就明确标注，不把新局证据冒充原局恢复。

每个安全节点、进入依赖步骤前及结束本局前检查台账：是否还有 worker 无结果、代码验证失败、未加载的补丁、未做 UI 复测的修复。**非阻塞仅允许过程并行，不允许带着未闭环 bug 宣布完成；阻塞修复没有结果前，不走受影响的下一步。** 若确实受外部条件限制无法修复，明确交付未完成/受阻与唯一解阻事项，不能宣称通过。

### 8.4 异常观察与暂停条件

以下阈值是本计划建议的**诊断检查点**，不是产品 SLA，也不是自动判失败规则：

- 单轮等待超过 3 分钟：记录截图、耗时和状态；若后台仍有可证实进展，继续观察。
- 超过 10 分钟且 UI、任务状态和可用只读日志均无进展：记疑似卡死，保留证据；仅通过产品可见的取消/重试/继续尝试恢复。不重复提交同一行动碰运气。
- 连续约 5 次有不同意图的真实行动仍得到同义重复、无新信息也无状态进展：记录循环候选。通过角色内的一个具体问题判断是否有可行方向；不额外编一条“救援指令”。

真实暂停/结束条件：

1. 到达规定终点后先清点修复台账；所有相关 worker 已结束且真实缺陷已修复复测，才可收尾。合理失败/离开结局的覆盖与回归目标另判，不靠修代码保证玩家赢。
2. 无法确认 Grok 4.6 low、无法导入/建卡、崩溃无法续玩、必要选项无法操作、持续卡死等产品阻塞：**暂停 → 修复 → 复测 → 恢复**，不是只写报告结束任务。
3. 连续重复或强制推进使当前玩法无法有效检验：保留失败现场，判断系统缺陷并修复；不得用提示词告诉 KP 正确答案来刷绿。
4. 外部服务、额度或执行时长不足：写明具体外部原因和已尝试的恢复路径，状态为受阻/未完成，不宣称产品通过，不虚构剩余剧情。

换成脚本、伪造 KP/回合/模型记录，标记 `invalid-for-acceptance`。看过隐藏答案影响行动或未实际偏离，则将相应玩法证据标无效/覆盖不足，而不是混进通过率。缺少某一种 UI 工具本身不是伪造证据，但不可用 mock/API 冒充替代。

接近上下文/时间上限时，保存当前界面、最后完成回合、战役与证据路径、下一步真实意图以及 bug 台账、worker ID/状态、补丁与复测状态，交给后续执行者续同一局；交接不代表 bug 已关。不要用总结代替未玩的结尾。

## 9. 证据与报告

### 9.1 存储原则

- 每局建立独立结果目录，例如 `<evidence-root>/<task-id>/<run-id>/`，保存 `report.md`、关键节点时间线和截图；另有持续更新的 bug 台账，保留发现、修复、复测全过程与失败尝试。
- `<evidence-root>` 由执行者记录一个真实绝对路径；使用新目录，不覆盖既有证据。
- 原始证据来自实际 Web/App 后端使用的 COC home 下 `campaigns/<id>/`、`modules/<id>/` 及实际会话日志；仓库源码模式才通常是 `.coc/campaigns/` 等路径。
- **不能假定 Web 与独立 App 使用同一 home，也不能假定独立 App 使用仓库 `.coc` 或 `.pi/coc-agent`。** 从实际会话/日志只读确认，报告真实位置；切换测试表面时确认战役身份，不把另一套数据当续局。不要修改复制数据来冒充原始状态。
- 留存现有 `turns/`、逐字记录、事件/收据、遥测等，不要求不存在的文件名一定出现。截图是 UI 证据，实际日志是行为和状态证据，两者相互对应。
- 模型验证分级：实际 play UI 所选值；可得的会话/请求元数据。只有 UI 证据时写“UI 确认，实际请求 effort 未证实”，不捏造 provider 实际收到 low。若证据显示模型或 effort 与要求不符，本次不作为合格条件下的通过。
- 不读取/复制密钥，不截图凭据页；证据中可能包含私人路径和剧情剧透，对外分享前脱敏，不公开上传原 PDF。

### 9.3 总表判定

- 九个任务分别判定，不用“总共跑了多少轮”代替覆盖，不把未执行/阻断从分母悄悄删掉。
- MAIN 通过：条件合格，真实到达规定终点，来源审计支持其为剧本/章节收束，且本任务确认的产品 bug 已完成修复/复测闭环。
- DETOUR/SIDE 通过：真实偏航已发生、五项适用核验通过、回归后到达规定终点，且本任务确认的产品 bug 已完成修复/复测闭环。
- 所有关联 worker 必须有终态结果；代码已修未加载、自动化绿但 UI 未复测、非阻塞问题仍在处理，都记未完成，不是通过。误报须有证据关闭，不能自行把真实缺陷降级成“以后再说”。
- 回归成功但未玩到终点，记“回归已证实，完成范围不足”，不是整个任务通过。
