# PipiCOC 桌面实机测试计划：主线、主动偏航与支线偏航

> 状态：待执行的测试委托，不是测试报告。本轮只编写计划，未启动 App、未开桌、未导入 PDF。
> 计划日期：2026-09-15。只读核对时源码为 `0.9.3a / 1318b1674`；这不证明已安装 App 来自同一提交。

## 1. 目标与成功定义

用户要知道：**PipiCOC 能否让真实玩家顺畅跑完剧本；玩家认真地偏离后，Grok KP 能否在保留选择、因果和既有状态的前提下，提供可信的回归路径并真正接回剧本。**

成功不是回合数够多，也不是 KP 宣布“故事结束”。必须有实际调查、选择、后果和可证明的收束。短本和鬼屋跑到结局；长本从开场开始，至少跑完一个完整调查章节。

偏航测试有两个独立结果：

1. **回归能力**：是否出现合理的连接机会，玩家因这个机会行动后，是否真正回到主线。
2. **自主性与连续性**：是否允许偏航，支线是否有内容与后果，回归时是否保留这些后果。

强制传送回主线、替玩家决定、修改已确立事实、用所有 NPC 重复催促，均不算“圆回来”。有逻辑的永久离开可以是合理故事结局，但不能记为“回归主线成功”。

## 2. 固定条件与方法边界

### 2.1 执行环境

- 被测对象：唯一安装包 `/Applications/PipiCOC.app`；bundle id：`com.leehow.pipicoc`。
- 交互方法：**computer use 操作真实桌面 App**，包括选模型、导入 PDF、建卡、开桌、输入玩家行动和选择结构化选项。
- KP：**Grok 4.6，thinking/effort = low**。若模型目录显示 provider，记录完整 provider/model id，预期模型为 `grok-build/grok-4.6`；不是 Grok 4 fast、其他 Grok 版本或执行 AI 自己。
- 玩家：负责该任务的外部 AI 主会话；只扮演一名认真玩的玩家。一次提交一个自然、连贯的行动或问句，等本轮完成再决定下一步。
- 默认玩家语言：简体中文。英文长本也用中文游玩，用于观察英文来源到中文游玩的连贯性；不人为要求逐句翻译。
- 每个任务新建独立战役，角色背景与能力尽量可比；不要求篡改骰子或复制存档来制造完全相同结果。
- 所有任务使用同一安装包版本。若中途修复或更新，旧局保留，重测另编运行编号，不把不同版本拼成一次通过。

本次用户明确指定 computer use，故本计划不采用仓库默认的 `tests/play/driver.py` 传输方式，也不改写默认验收契约。此授权仅覆盖真实 GUI 测试，不授权假守秘人、批量脚本或合成回合。

### 2.2 允许与禁止

**允许：**桌面截图、无障碍元素操作、键盘与鼠标；只读核对实际日志/战役状态；测试后由独立审计 AI 对照原始剧本。日志读取仅辅助举证，不代替 GUI 体验。

**禁止：**

- 用 RPC、CLI、浏览器开发页、开发者控制台、直接 provider 调用或脚本绕过被测 GUI 来开桌/行动/结算/切模型。
- 修改源码、配置、战役状态、会话 JSONL、模型切换记录或模组图来让测试通过。尤其不能伪造 `model_change` 或 effort 记录。
- 执行 AI 自己写 KP 回答、代掷骰、补造线索，或安排第二套 Keeper 接管故事。
- 预先生成一串玩家台词、批量发送、关键词路由、固定场景模板刷回合。下面的玩法策略不是脚本。
- 玩到一半读隐藏模组图或 PDF 解答，再把答案用于玩家行动；把审计结论、计划或“请把我拉回主线”发给 KP。
- 为重新开始而删除旧战役、逐字记录、遥测、模组数据或测试证据。
- 擅自打包、安装第二份 App、更新产品或重启 PipiUI 宿主。故障在本任务中记录，不顺手修复。

若执行 AI 没有 computer-use 能力，报告缺少的能力并退回任务，不得自行改成 API 或命令行测试。

## 5. 派工与信息隔离

- 推荐每个任务交给一个新 AI 会话，传本计划 + 一个任务 ID；模型与成本由执行方安排，KP 始终是 App 内 Grok 4.6 low。
- 同一台电脑、同一 App **一次只能有一个桌面执行者**。不同聊天会话或不同战役，不代表鼠标、窗口、全局设置已隔离。默认串行，不要九个 AI 抢桌面。
- 可分给三名 AI 各负责一个剧本的三个任务，但每局用新玩家上下文；已读过前一局结局的玩家必须标注“非盲测”，不能声称未知剧情。
- 独立机器和数据目录已经隔离时才并行。不要为了本计划自行创建另一份本机 App。
- 推荐执行顺序：H-MAIN → A-MAIN → M-MAIN，先验证三条开桌路径；再依次执行 H/A/M 的 DETOUR、SIDE。某个剧本被阻断，不因此停止其他已可执行任务。
- **玩家与审计分离**：玩家游玩期间只使用 UI 给出的公开信息。独立审计 AI 在每局结束或真实阻断后，使用只读副本对照原始 PDF/内置来源和日志，不把隐藏事实反馈给仍在游玩的玩家。
- 审计 AI 不使用正在被执行者控制的桌面、不修改数据、不接管 KP；读 PDF 时保留页码/来源位置。剧情判断是语义审计，不能用关键词计数替代。

## 6. 每局通用流程

### A. 开局与证据锚定

1. 用 computer-use 的应用选择工具激活 `com.leehow.pipicoc`，确认实际目标是 `/Applications/PipiCOC.app`，不是 PipiUI、源码开发页或另一个构建。
2. 记录本局 `task_id`、唯一 `run_id`、开始时间/时区、App 版本/可得的构建身份、屏幕环境。无法取得构建 SHA 就写“未知”，不要拿源码 HEAD 代替。
3. 通过输入栏模型选择器和 thinking/effort 控件选 **Grok 4.6 / low**；截图保留选择结果，不捕获凭据。
4. 若 low 不在列表，或选后无效，先用新截图、无障碍元素或键盘重新确认。两次可靠尝试仍不能成功，记录配置阻断，不改文件、不偷偷换模型/effort。
5. 经新建流程选中文、内置鬼屋或指定原 PDF，正常完成建卡。记录导入开始/结束、可见进度、失败提示与重试情况。正常支持的继续/重试可以使用，但须保留首次失败证据。
6. **进入实际游玩会话后再次核对 Grok 4.6 / low。** 建卡/setup 和 play 可能不是同一个会话，不能拿建卡窗口截图证明 KP 的设置。没有满足条件前不发首句玩家行动。
7. 记录战役名称/id、模组关联、会话标识。GUI 不显示 id 时可只读从日志定位；不得写回。

computer-use 操作优先级：新观察 → 无障碍元素/键盘 → 必要时像素。不要照抄旧截图坐标。元素失效先重新观察；同一做法连续失败两次就换方式，不盲点。原生文件选择器可用“前往文件夹”输入精确路径。不得改用接口跳过操作问题。

### B. 正常玩一回合

1. 阅读 KP 本轮完整输出和结构化规则选项。
2. 以角色当前知道的事，决定一个行动/问句；输入并发送一次。
3. 等待本轮结束；忙碌时观察状态，不重复点击发送，不提前排队下一回合。
4. 观察叙事、骰子/机制卡、人物卡/资源、线索和场景变化是否一致，再做下一步。
5. 关键节点截图：开场、重要线索、首次实际检定、状态变化、偏航开始、支线后果、回归机会、实际回归、结局/章节收束、任何故障。

不规定“必须 N 回合”。真实决策和因果链才是覆盖。正常等待不是产品失败；异常延迟要记录时间，不用快速刷输入掩盖。

### C. 跨回合顺带观察（不为凑覆盖硬造情节）

| 能力 | 可观察证据 |
|---|---|
| 玩家行动准入 | KP 不替玩家实施未选择的关键行动；建议、猜测与已经行动区分清楚 |
| 数值与状态 | 需要结算时有机制卡/收据；人物卡的 HP、SAN、物品等与实际后果一致；无凭空恢复或重复扣减 |
| 信息与保密 | 新线索有取得过程；猜测不直接升级为模组事实；不提前泄露隐藏答案 |
| NPC 与连续性 | 称呼、动机、关系、承诺及已知信息跨回合保持一致 |
| UI 与阅读 | 正文中文可读；数值/规则选择有专用结构化呈现，不靠正文复述替代；无重复正文、消失的选项或无法输入 |
| PDF 路径 | 导入可理解；需要新区域资料时能继续；没有把缺资料静默编造成权威剧本事实 |

没有自然发生的战斗、疯狂、推骰等记“未覆盖”，不强迫发生，也不据此扩张本计划。读页/补读是否真的发生由实际日志辅助证明，不能单凭流畅文风断言。

## 7. 三种玩法的执行策略

### MAIN：主线完成能力

- 接受合理的初始动机，正常询问、搜集线索、访问有关人物/地点，根据公开信息推进。
- 遇到失败检定或暂时死路，像认真玩家一样尝试替代调查，而不是请求剧透、自动成功或跳到结局。
- 可以提出角色合理问题，不故意拉出无关目标，也不牺牲基本谨慎来赶进度。
- 终点应包含调查结果、关键冲突/选择的后果及可辨认的故事/章节收束。
- 合乎规则的失败结局可以算“到达结局”，但须区分游戏失败与产品失败。若开场就死亡/退场，不能拿这条捷径宣称主线能力充分覆盖；保留原局，标覆盖不足，需要补测则新建局。

### DETOUR：有意离开主线

1. 先进行足够的正常开场，让玩家知道当前调查目标以及至少一条可行线索；在测试笔记中记录，不发给 KP。
2. 从眼前真实情境选择一个有角色动机、但不沿当前线索推进的目标。例如处理生计、寻找另一份委托、调查不相关的疑点或准备离开当前调查地点。**选择随现场生成，不照抄示例，不凭空宣称不存在的地点/NPC。**
3. 真正投入行动，让偏离有时间、地点、资源或关系上的后果。只说一句“不去了”然后马上回头，不算已测试偏航。
4. 不主动提醒 KP“这局在测试回归”，不自己凭攻略设计回归桥梁。允许拒绝一次牵强的催促，但不无条件拒绝所有新信息。
5. 一旦出现角色会在意的合理新机会，按角色动机作选择；若愿意接触，就沿它继续，观察是否回到原案的实质调查。
6. 返回后继续到本任务终点；仅 NPC 再提剧本名、任务提示复读或玩家口头答应，不算实际回归。

### SIDE：认真做支线，再自然跑偏

1. 从真实游玩中出现的次要人物、承诺、物品、地点或疑问中选一项值得认真追究的目标；不要先读 PDF 挑“官方支线”。
2. 真正帮助、追查或履行承诺，观察其是否有具体信息、人物动机、选择与后果，而非一问即空。
3. 顺着这个目标的新因果再走一步，让它成为与原调查不同的行动方向。测试笔记明确标出“支线开始”和“支线导致偏离”的分界。
4. 看 KP 是否把支线形成的人脉、代价、信息或时间后果合理连接回原案，而不是取消支线、瞬移人物或忽略之前做过的事。
5. 对可信回归机会按角色逻辑回应；回归后主动使用这条支线已经获得的东西或承担其后果，检查连续性，再继续到终点。

若 KP 从不允许形成真实支线，或所有问题都被敷衍后赶回原案，记录支线能力失败；不要由玩家自己编一个支线冒充产品交付。

### 对“圆回去”的五项核验

| 维度 | 通过表现 | 失败信号 |
|---|---|---|
| 允许偏离 | 玩家选的行动真正进入故事并产生后果 | 否认选择、替玩家行动、强制传送 |
| 支线质量（SIDE） | 有具体对象、目标、信息/代价和可延续后果 | 空泛寒暄、循环回复、一次性填充 |
| 因果连接 | 回归机会来自既有人物/线索/世界变化，或合理的新因果 | 所有人突然掌握同一秘密、无来源送答案、反复“必须回去” |
| 状态保留 | 时间、资源、物品、关系、承诺延续 | 为接回主线抹掉行动、改写既定事实 |
| 实际回归 | 玩家自愿行动后重新推进原案的有效节点 | 只说“回归主线”，没有新的调查进展 |

每项写“通过/失败/未证实”及一个具体回合锚点，禁止只给模糊总分。新增支线本身不等于违背剧本；审计关注是否破坏核心真相、既定事实或公平性，不要求照搬场景顺序。

## 8. 停止、阻断与不充分结果

以下阈值是本计划建议的**诊断检查点**，不是产品 SLA，也不是自动判失败规则：

- 单轮等待超过 3 分钟：记录截图、耗时和状态；若后台仍有可证实进展，继续观察。
- 超过 10 分钟且 UI、任务状态和可用只读日志均无进展：记疑似卡死，保留证据；仅通过产品可见的取消/重试/继续尝试恢复。不重复提交同一行动碰运气。
- 连续约 5 次有不同意图的真实行动仍得到同义重复、无新信息也无状态进展：记录循环候选。通过角色内的一个具体问题判断是否有可行方向；不额外编一条“救援指令”。

真实停止条件：

1. 已完成规定终点；或失败/离开形成合理结局，但相应覆盖/回归目标未达成，应分别记录。
2. 无法确认 Grok 4.6 low、无法导入/建卡、崩溃无法续玩、必要选项无法操作、持续卡死等阻断。
3. 连续重复或强制推进已经有充分证据，当前玩法无法继续有效检验。保留失败局，可在自然可行的情况下继续收集终点证据，但不要纠正 KP 来刷绿。
4. 外部服务、额度或执行时长不足。写明外部原因，状态为阻断或未完成，不宣称产品通过，也不虚构剩余剧情。

没有 computer-use 能力、换成脚本、伪造 KP/回合/模型记录，标记 `invalid-for-acceptance`。看过隐藏答案影响行动或未实际偏离，则将相应玩法证据标无效/覆盖不足，而不是混进通过率。

接近上下文/时间上限时，保存当前界面、最后完成回合、战役与证据路径、下一步真实意图，交给后续执行者续同一局；不要用总结代替未玩的结尾。

## 9. 证据与报告

### 9.1 存储原则

- 每局建立独立结果目录，例如 `<evidence-root>/<task-id>/<run-id>/`，保存 `report.md`、关键节点时间线和截图。
- `<evidence-root>` 由执行者记录一个真实绝对路径；使用新目录，不覆盖既有证据。
- 原始证据来自 App 实际使用的 COC home 下 `campaigns/<id>/`、`modules/<id>/` 及实际会话日志；仓库源码模式才通常是 `.coc/campaigns/` 等路径。
- **不能假定独立 App 使用仓库 `.coc` 或 `.pi/coc-agent`。** 从实际会话/日志只读确认，报告真实位置；无法确认则写未知。不要复制生产数据再修改，冒充原始状态。
- 留存现有 `turns/`、逐字记录、事件/收据、遥测等，不要求不存在的文件名一定出现。截图是 UI 证据，实际日志是行为和状态证据，两者相互对应。
- 模型验证分级：实际 play UI 所选值；可得的会话/请求元数据。只有 UI 证据时写“UI 确认，实际请求 effort 未证实”，不捏造 provider 实际收到 low。若证据显示模型或 effort 与要求不符，本次不作为合格条件下的通过。
- 不读取/复制密钥，不截图凭据页；证据中可能包含私人路径和剧情剧透，对外分享前脱敏，不公开上传原 PDF。

### 9.2 每局报告模板

```text
任务 ID / 运行 ID：
状态：未执行 / 进行中 / 通过 / 失败 / 阻断 / 覆盖不足 / 无效
开始与结束时间、时区、实际耗时：
App 版本与可得构建身份（未知项写未知）：
KP provider/model、thinking、确认时点与证据等级：
玩家语言 / 角色概要 / 是否盲测：
战役 ID / 会话 ID / 模组 ID / 真实证据绝对路径：
首次导入还是缓存复用；setup/play 是否复核模型：

完成范围：
- 开场起点；目标结局/章节；实际终点。
- 实际经过的关键调查、选择和后果。
- 长本：原 PDF 章节名、页码范围及章节收束证据（审计补充）。

偏航证据（MAIN 可不适用）：
- T?：原调查目标与已知线索。
- T?：偏离开始；玩家原话；KP 实际回应。
- T?：支线投入、获得内容与实际后果（SIDE）。
- T?：回归机会；为什么合理/不合理。
- T?：玩家作何选择；何时真正推进原案。
- T?：回归后的支线后果/状态是否保留。
- 五项核验逐项结论与证据。

问题列表：
- 编号、严重度、类型、首次发生时间/回合。
- 前置条件 → 界面操作/玩家原话 → 实际结果 → 期望结果。
- 截图/日志路径、是否阻断、GUI 恢复是否成功。
- 观察到的事实与原因猜测分开；不将猜测写成根因。

审计：核心真相/章节边界/状态连续性的来源锚点；合理改编与矛盾区分。
未覆盖/未证实事项：
若需续测：最后一个已完成回合、当前窗口、下一步角色意图。
最终结论及尚需重测的具体点：
```

问题严重度：**阻断**（无法继续或数据/授权边界严重破坏）、**主要**（能继续但剧情/规则/回归能力实质失效）、**次要**（不影响推进的呈现/易用性问题）。问题类型至少区分 UI、模型/配置、PDF/资料、规则/状态、KP 叙事/回归、外部环境。

### 9.3 总表判定

- 九个任务分别判定，不用“总共跑了多少轮”代替覆盖，不把未执行/阻断从分母悄悄删掉。
- MAIN 通过：条件合格，真实到达规定终点，来源审计支持其为剧本/章节收束，且无未解决的主要缺陷。
- DETOUR/SIDE 通过：真实偏航已发生、五项适用核验通过、回归后到达规定终点，且无未解决的主要缺陷。
- 回归成功但未玩到终点，记“回归已证实，完成范围不足”，不是整个任务通过。
- 合理离开/失败结局、KP 完全丢失主线、强拉回主线，三者分开写；不要笼统写“没回来”。
- 若缺少来源审计或请求参数证据，明确证据限制，不把模型流畅输出当事实保证。
- 同类问题跨剧本出现时，归为候选系统问题，附各任务证据；不要让测试者手改三份内容掩盖它。
- 九局是一次结构化探索样本，不是稳定性概率证明。修复后的回归另开 run，保留原失败结果。
