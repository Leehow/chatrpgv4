# Enhanced Locations

Use place for location work. Natural-language travel may reach compatible unregistered places: establish only the minimum observable structure and enter in one command. Reuse known identities. A feature or corner can be a local position. Read place {op:"inspect",need:"contract"} for detail when needed.

## Identity and structure

First judge the player's intended scale and existing source: a known place, a child place, or a feature in the current place. Inspect a remote place by name without moving. Source coverage gaps are not evidence that an ordinary place cannot exist. Use source or Historical Reference for a concrete question about established truth or the period; ordinary improvisation needs no separate generator. Jev's supplied matching is advisory, never a veto. Do not replace a named authored place with an invented lookalike.

For a new place, supply additions parent before child: {name,within,description,features?}. within explicitly names the containing place, or null for no registered parent. Omission never means the room being left. A child's qualified name is its parent's name followed by " / " and its leaf name. Use that qualified name to move to a new child. Two hotels may each have Room 203. New descriptions are public observable facts, not secrets or scripted narration. Do not enumerate an entire building in advance.

## Travel and local position

Submit change {action:"move",to,via?,travel_band?,at?,relation?,additions?}. The native output command uses the same fields plus kind:"place". No issued destination list exhausts the world. Explain an unlisted route in via. Choose a supplied travel band when a real journey needs time; containment in one city does not imply free travel. A known lock or impassable feature is a real obstacle, not a registration failure. Do not move through it without first resolving the obstacle. A failed transaction moved nobody.

To approach the front desk, move to the same place with at:"front desk",relation:"beside". Inspecting or looking toward it never changes position. Rooms that matter independently may be child places; counters, windows and corners normally remain features. Features are not carried inventory. Returning reuses their current state. Update an existing feature with {action:"feature",to,at,state?,passable?} after the corresponding authorized action; do not change its original description or invent new facts through an unrelated update.

## Continuity and authority

One submit can create a compatible destination and enter it atomically. Mixed-domain apply uses the same kind:"place" effect. The kernel owns IDs, receipts, time arithmetic and atomicity; the Keeper owns semantic intent, consistency and minimal creation. Do not author receipt IDs, force source changes, use a generic JSON patch, or convert every turn into a location read. The sole final author uses committed appearance, features, position and outcomes. A disabled Mod preserves readable places but does not accept enhanced writes.

Establish alone registers surroundings and moves nobody. When the player goes to a new room, use action:"move" with the room in additions and its qualified name in to. Time or NPC presence updates do not substitute for that arrival receipt.

For a feature-only addition to an existing authored place, omit its description and supply only its name plus missing features. Source appearance is not replaced. When a route crosses an existing boundary, bind through:{place,feature}; its current passable:false is a concrete obstacle. Describe and resolve the player's actual attempt before changing that feature's state. An alternate route is a separate fictional claim for the Keeper to judge, not a way to clear a lock flag.
